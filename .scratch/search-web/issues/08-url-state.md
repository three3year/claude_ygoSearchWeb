# 08 — 網址狀態

**What to build:** 一行網址就能把「所有暗屬性的誘發即時特招」丟給別人。按下搜尋時條件被
寫進 `#hash`,收到連結的人一開就看到結果而不是空表單;試了幾輪條件之後能用「上一頁」
回到前一次的設定。

效能上不是問題:寫入是一次字串組裝加一次 DOM 屬性賦值,相比之下一次搜尋要掃 14,207 張卡、
32,637 個[[效果句]],兩者差好幾個數量級。

兩個實作陷阱都要處理:

1. **自己寫 hash 會觸發 `hashchange`**,沒擋掉就會再跑一次搜尋(同一次搜尋跑兩遍)。
2. **打字時不寫 hash**,只在按搜尋時寫一次,否則瀏覽器歷史會被每個 keystroke 塞爆。

**Blocked by:** 05 — 卡片參數軸、06 — 效果類型與必發選發軸、07 — 排序

**Status:** resolved

- [x] 按搜尋時把全部條件序列化進 `#hash`,`pushState` 語意(留瀏覽器歷史)
- [x] 帶條件的網址一開就還原條件**並自動執行搜尋**
- [x] 三態排除可雙向編碼(包含/排除/未選三種狀態往返後不變)
- [x] 排序狀態也進 hash
- [x] 自寫 hash 觸發的 `hashchange` 被擋掉,搜尋只跑一次
- [x] 打字過程不寫 hash
- [x] 「上一頁」回到前一次的條件與結果
- [x] 壞掉或過期的 hash(欄位名不認得、值不在值域裡)不讓頁面崩掉,忽略該段條件
- [x] 接縫 3 測試:任意條件組合序列化後再解析回來必須相等(往返測試,含三態排除)

## Comments

2026-08-14 實作完成。新增 `web/js/hash.js`(純模組:`{ q, sort }` ⇄ 字串,不碰 DOM、
不讀 `location`),`web/js/query.js` 多一個 `write()`(`read()` 的反向,網址還原條件走它),
`web/js/main.js` 接上寫入時機與 `hashchange`。接縫 3 測試多 8 條(共 70 條);
`web/data.js` 不變——這一票沒有動索引。

**網址的參數名就是查詢條件的鍵名,條件軸由 `Query.FIELDS` 導出。** `#name=青眼&cat=m&
attr=-light,dark&atk=2500-&sort=atk` 讀得懂,而且加一條條件軸時網址自動認得它。抄一份
參數對照表在 `hash.js` 裡的話,新軸會安靜地不進網址——**分享出去的連結少了一個條件,
而收到連結的人不會知道少了什麼**,這與 ADR-0008 擋的是同一個失效模式(值域漏一碼、
某批卡無聲消失)。三態的三個狀態都寫得出來才回得來:`-` 前綴是排除、沒前綴是包含、
不出現是未選(未選也是一個狀態,只是它的寫法是缺席)。

**擋自寫 `hashchange` 用的是「上次寫了什麼」的正規形,不是布林旗標。** 旗標擋不住
「寫進去的值與現況相同、瀏覽器根本不發事件」那一次——旗標會留到下一次使用者真的按
上一頁時把那一次吃掉,而那是個看不出原因的「上一頁沒反應」。比正規形而不是原字串,
是因為瀏覽器對 hash 的百分比編碼各有各的作法(有的原樣留著中文、有的編起來),
自己寫進去的那一個讀回來不見得長得一樣,於是被當成別人改的而重跑一次搜尋。
`Hash.canon()`(解析一遍再寫回去)因此是主流程唯一需要的判準,而它是純的、測得到。

**寫入時機三處:按搜尋、清除條件後的重搜、換排序。** 打字不寫(否則每一個 keystroke
都塞一項進瀏覽器歷史),載入不寫(開站時只讀,不留一個一模一樣的歷史項)。
排序也寫是因為「最高攻擊力的暗屬性誘發即時」這個問題的答案有一半在排序上——只在
搜尋時寫的話,換完排序再把網址丟給人,對方看到的是領域序。呈現層自己不知道有網址
這回事:`View.initSort(onChange)` 只回報「排序被換過了」,要不要記進網址是主流程的事。

**分頁位置與每頁筆數不進網址。** 那是「這一頁看到哪」而不是「查了什麼」,寫進去等於
連對方該從第幾頁開始看都替他決定了。

**條件的碼照值域的宣告序寫,不照點擊順序。** 同一組條件只有一個網址,兩個人因此比得
出來查的是不是同一件事;`canon()` 能當判準也是靠這條(同一個狀態只有一種寫法)。
手改過或參數順序不同的網址在按下搜尋之後收斂成正規形——`push()` 比的是網址列上那個
字串本身,一樣就不寫(不多留一個一模一樣的歷史項),不一樣就寫(網址不會留在那裡
說著另一件事)。

**壞掉的一段只丟那一段。** 認不得的欄位名、不在值域裡的碼、讀不出數字的範圍、壞掉的
百分比編碼(`decodeURIComponent` 會丟例外)一律忽略該段,其餘條件照常生效。網址是
使用者手上會被改到、也會隨值域改版而過期的東西,而壞掉的一段不值得一片白畫面。
還原到側欄時同一條規則再走一次:**收著的軸不寫**——帶了子類型卻沒帶大類的網址,
那一段不生效(看不見的條件是解釋不了的零結果),必發/選發在沒選承載型效果類型時同理。

**網址寫的是「畫面上這批結果的條件」而不是側欄當下的樣子。** 側欄可以領先畫面
(打了字還沒按搜尋),而那時換一下排序就會把還沒生效的條件寫進網址——收到連結的人
得到的結果與分享的人看到的不是同一批。所以 `run()` 記下這一次跑的條件,`push()` 寫它。
這不是「上次查詢的中間結果」那種全域,只是那一次的條件本身;結果仍然每次重跑。

**DOM 那一側以拋棄式冒煙對過**(最小 DOM + 假的 location/history + 真實 `data.js`,
先例是票07),15 項:空網址開站只跑一次搜尋且不寫網址、打字不寫、按搜尋只跑一次、
三態進網址、換排序更新網址但不重跑引擎、上一頁逐層回到前一次的條件與排序、
別人給的網址還原條件與排序選單並自動搜尋、過期的子類型/必發選發那兩段失效、
範圍與 `?` 與卡名語言還原、壞網址不崩、清除條件後網址回到空的、同條件搜兩次不留兩個
歷史項、打了字沒搜尋就換排序時網址寫的仍是生效中的條件、側欄 → 網址 → 側欄的往返。

**驗證階段抓到三個真的錯**,都已修並補上防止復發的斷言:

1. `push()` 原本比的是正規形,於是停在一個非正規的網址上時,按下清除條件後網址列
   不會跟著清掉(畫面空了、網址還寫著條件)。改成比網址列上那個字串本身。
2. 換排序時 `push()` 直接讀側欄,把還沒按搜尋的條件寫進網址(上一段)。
3. `=1` 這種沒有欄位名的段會比對到第一個沒有 `?` 條件的範圍軸,在條件物件裡留下一個
   空鍵名的殘骸。改成欄位名為空就整段忽略;測試因此改成斷言**壞掉的段不留任何殘骸**
   (與乾淨的網址解析出來的物件逐欄相等),而不只是「其餘條件還在」。

瀏覽器上的實際歷史行為(上一頁/下一頁、分享的網址在另一台裝置開)仍走人工驗收,
見票10。
