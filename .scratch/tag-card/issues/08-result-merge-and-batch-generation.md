# 08 — 拆句表、判定結果合併與批次檔

**What to build:** 判定工作變得可執行的**機制**。建置流程能讀[[拆句表]]把舊式無編號整團切開、能把判定票寫回的結果檔合併進[[效果標記表]]、能吐出批次檔。本票**完全不需要任何判定**——三道驗證與兩個新參數都可以用合成 fixture 純 TDD 做完。

關鍵契約:判定結果**可以改變效果句的集合**,不只是填 `kind`。但改變集合這件事不由判定結果檔做,而是由獨立的[[拆句表]] `data/clause_splits.json` 做(ADR-0003)——`splits` 決定效果句的**集合**、`judgments` 決定效果句上的**值**,兩者生效時機不同:拆句表在[[官方明示]]抽取**之前**,判定結果在**之後**。

**Blocked by:** 03 — 官方明示:五階梯歸屬與類型抽取、04 — 必發/選發規則層、05 — 重跑保留語意

## Comments

原票面把「判定結果可以替換某卡的整組效果句」寫成 `judgments` 參數的能力。grilling 後改為獨立的拆句表,理由寫在 ADR-0003:責任分離(骨架永遠負責「卡文 → 效果句」、判定永遠負責「效果句 → 類型」),以及「拆完之後重跑官方明示」在單一參數之下每次都得先重算一遍拆句才跑得動。

拆句表記卡文雜湊這件事,對「偵測變動」其實是**冗餘的**——無遺漏覆蓋等式已經涵蓋任何一個字元的變動。留著是為了**診斷**:出事時能一眼看出這筆拆點是對著哪一版卡文切的。

### 實作

管線(`tagcard.py`):`split_hash()` 是公開的,寫拆句表的程式與讀拆句表的骨架共用同一支,兩邊不會各算各的。`_validate_split()` 一次跑完四道關卡並回傳各段的 span,拆出來的文字一律從原文切片而不是照抄判定者給的字串——「連續子字串」這條不變式因此不靠判定者的自律,而是結構上不可能違反。

`official.attest()` 多收一個 `unsplit` 參數。連帶三處跟著改,都是同一個病因(「有編號」被當成「已經是獨立效果句」的代理):

- 階梯四、五的排除條件從 `index == "1"` 改看 `unsplit`(票11 的正式修法)。
- `_match_quote` 的對位範圍從 `_numbered(effects)`(index 首字是①②③)改成 `attributable`(不在 `unsplit` 裡的效果句)。**這是拆完之後官方明示回得來的主要通道**——拆出來的段 index 是 `"1"` / `"2"`,舊寫法一條都對不到。
- `_seq_target()`:官方對舊式卡仍以『①』『②』稱呼,現在對得回拆出來的 `"1"` / `"2"`。未拆整團維持原本的行為(整團就是官方口中的那一個)。
- 效果外文本的明示從只看單一前言段改成掃全部 `"0*"` 段——拆句會生出 `"0-2"`。

判定結果走 `_apply_judgments()`,夾在官方明示與必發/選發之間。必發/選發因此從三層變四層:官方明示 → 判定 → 日文發動子句規則 → 留 null。判定給了 `optional` 但類型不承載時丟棄並進報告,值域規則優先。位置規則已經定案的效果外文本段不被判定覆蓋(結論不同時只進報告)——那一段的類型是位置決定的,不是判定的工作。

### 兩支新的 CLI 薄殼

- `make_batches.py` —— 即時跑一次管線再切批,判定票因此永遠吃到最新的影子預測與最新的效果句集合。`--dry-run` 只點數。批次檔自帶 `result_format` 範例,判定票不必回頭查任何來源(spec Story 36)。
- `merge_judgments.py` —— 判定票寫**一個**結果檔,這支把拆點路由進 `data/clause_splits.json`、把類型路由進 `data/tag_cards.json`。三道關卡任一不過就整批不寫入:集合一致性自檢、拆句表三道驗證、判定對得回效果句。拆句表的雜湊由這支對著**當下的**整團原文算,不是照抄判定者給的,所以「判定者拿著過期批次作答」會在關卡二被擋下來。
