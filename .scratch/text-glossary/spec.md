# 卡文詞彙表(text-glossary)

Status: ready-for-agent

2026-08-24 盤問定案(/grill-with-docs),同日 /to-spec 成稿。

## Problem Statement

翻譯與審查卡文時的用語決定散落各處:文本格式規範 §3.19 只有 6 條詞彙對照;
歷批審查檔「改寫依據」節累積的計數裁示(「，隨後」267:0、「再次召喚」32:0 等)
一批一份、不被下一批繼承。站主要翻譯或審查新卡譯文時,沒有一份集中、可查、
可比對的詞彙依據;譯文是否用了規範譯法,目前只能憑記憶與逐案翻查。

## Solution

建立**卡文詞彙表**:一份日→中逐條對照文件,收譯詞與句式模板兩級條目,每條帶
規範譯法、禁譯、庫內計數佐證與例外清單。AI 翻譯新卡時照表參照;站主人工翻譯
與審查時查閱;報告式驗證腳本拿它比對現有譯文、列出不一致供站主裁示;每批翻譯
後由 agent 提補充案、站主審定,讓詞彙表隨工作長大。首跑對全部新格式新卡做一次
全掃,產出不一致報告。

## User Stories

1. 作為 AI 翻譯 agent,我要一份機器可解析的譯詞對照表,以便翻譯新卡時每個術語都用站上規範譯法。
2. 作為 AI 翻譯 agent,我要每條譯詞附禁譯欄,以便主動避開曾見或易誤的錯誤譯法。
3. 作為 AI 翻譯 agent,我要常用句式的中日模板,以便整句句型(如「1ターンに1度」)譯得與全庫一致。
4. 作為站主,我要人工翻譯或審查時能查一份集中的詞彙表,以便不必翻歷批審查檔找過去的裁示。
5. 作為站主,我要每條條目帶庫內計數佐證,以便爭議時能回溯「規範 N 張 vs 禁譯 M 張」的實證依據。
6. 作為站主,我要歷批審查檔散落的句式裁示被收編入表,以便過去的裁示不再隨批次埋沒。
7. 作為站主,我要初始建表由 agent 從新格式新卡語料萃取高頻條目、我逐條審定,以便一次審得完且條目有實據。
8. 作為站主,我要每批翻譯後 agent 把遇到的新術語連建議譯法列成補充清單給我審,以便詞彙表跟著工作演進而不遺漏長尾。
9. 作為站主,我要一支報告式驗證腳本比對現有譯文與詞彙表,以便系統性找出用詞不一致,而不是靠人眼掃 8,156 段。
10. 作為站主,我要驗證報告依條目分組並附卡片密碼、卡名、中日原句,以便逐條裁示「要修/不用修」。
11. 作為站主,我要把裁示「不用修」的卡記入條目例外欄(附理由),以便重跑報告時不再重複出現、裁示不流失。
12. 作為站主,我要驗證只出報告不擋建置,以便語境合理的例外不會卡死管線。
13. 作為站主,我要詞彙表解析失敗時腳本大聲失敗,以便表格格式壞了立即發現而不是靜默漏檢。
14. 作為站主,我要確認為誤譯的修正走既有勘誤機制進站,以便修正有票號、可回溯、建置期校驗。
15. 作為站主,我要詞彙表與文本格式規範分工明確(逐條對照歸表、結構規則歸規範),以便每批新裁示知道歸檔到哪裡。
16. 作為維護 agent,我要 §3.19 原處只留指標,以便詞彙對照只有單一來源、不會兩處失同步。
17. 作為網站使用者(未來),我要在網站上查詞彙對照,以便讀懂卡文術語的來源與譯法——本輪只要求資料格式為此留路。

## Implementation Decisions

- **卡文詞彙表本體**是 `docs` 下的獨立 markdown 文件(`text_glossary.md`),
  表格格式嚴格,驗證腳本直接解析 md;未來上網站再由建置期解析產 JSON。
  單一來源,不設平行的 JSON 副本。骨架已建,含體例說明與 §3.19 六條收編。
- **條目體例**:譯詞條目七欄=日文/規範譯法/禁譯/庫內計數/PSCT(選填)/
  例外/備註;句式條目同欄,但日文與中文欄寫帶佔位符樣式:`〈n〉`=半形
  數字、`〜`=任意內文。例外欄是卡片密碼逗號清單,理由記備註。
- **分工界線**:逐條對照(譯詞、句式模板)歸卡文詞彙表;結構規則(標點、
  語序、換行、圈號體例)留文本格式規範。§3.19 原處改為指標(已改)。
- **初始建表**:語料=三級分類「新格式新卡」層(8,156 段)的中日句對照,
  取自效果標記表資料;高頻先行(建議門檻 ≥20 張)約百餘條;計數佐證母體
  沿審查檔慣例=含①新式段。agent 產仿 text-rewrite 三欄體例的審查檔,
  站主逐行審查、退回迭代到放行,放行後入表。歷批審查檔散落裁示一併收編。
- **驗證腳本**:新開 script 子目錄(循每目錄一線的現有慣例)。報告式、
  不阻擋建置(與分類器「偵測樣式服務分群,不是建置關卡」同精神)。檢查
  兩級:譯詞(日文側含原詞而中文側未用規範譯法或用了禁譯)與句式(日文
  側命中樣式而中文側未照模板)。例外欄所列卡自動跳過。佔位符→機器比對
  規則的推導由腳本定義並記於 docstring,md 只維護人讀樣式。詞彙表解析
  失敗(欄數不符、佔位符不明)必須吵出來。
- **報告**:依條目分組,每筆含卡片密碼、卡名、命中條目、日文句、中文句,
  末尾附規模與型態摘要(總筆數、依條目分布、誤報比例抽樣評估)。
- **首跑**:全掃 8,156 段新格式新卡。待審佇列怎麼切(是否另開稽核
  feature、仿 wayfinder 分子批)看報告實際規模再定,不在本 spec 定案。
- **修正管道**:確認為誤譯的修正走卡文勘誤表機制進站(勘誤=修誤譯改
  內容),不動文本改寫表。
- **維護**:每批翻譯後 agent 提補充案+站主審;條目變動以「審查批改」
  commit,慣例同文本格式規範。
- **文件**:CONTEXT.md 詞條「卡文詞彙表」已登錄;不立 ADR(決定皆可逆,
  本 spec 已記錄)。正式名稱「卡文詞彙表」,勿用翻譯詞彙表/譯詞表/
  用語表;與值域正典(搜尋介面 enum 對照)同名不同物。

## Testing Decisions

- **接縫(2026-08-24 站主確認)**:單一高接縫——一個純函式,輸入詞彙表
  md 全文字串+合成卡句記錄(text_ja/text_zh 對),輸出結構化不一致清單。
  解析、譯詞比對、禁譯、佔位符、句式樣式、例外跳過全部從這個接縫驗;
  CLI 與報告排版是薄 IO 殼,不測。
- **好測試的標準**:只斷言外部行為(餵什麼進、報什麼出),不斷言中間
  entries 結構等實作細節;合成記錄、不做 IO。
- **先例**:text_format 的 test_classify.py(純函式餵合成卡片記錄)、
  tag_card 的 test_sync_errata.py;測試檔與腳本同目錄同置,unittest,
  中文 docstring 註明依據票號。
- **必蓋案例**:譯詞命中且照規範(不報)、未照規範(報)、用禁譯(報)、
  例外卡跳過、`〈n〉` 佔位、`〜` 佔位、句式日文命中中文照模板(不報)、
  未照模板(報)、解析失敗吵出來、多條目命中分組。
- 檔尾可循 test_classify.py 先例加一條對真實資料的輕量迴歸,不作為主體。

## Out of Scope

- 網站前端的詞彙表顯示(未來另開線;本 spec 只要求 md 格式嚴格可解析,為此留路)。
- 全掃後待審佇列的分批管理與逐筆修正執行(看首跑報告規模再定,屆時另開票或另開 feature)。
- 舊式卡文翻新(text-rewrite 線)與其審查流程。
- 阻擋式建置檢查(驗證永遠是報告式)。
- 低頻長尾條目的窮舉(靠每批維護機制逐步入表)。
