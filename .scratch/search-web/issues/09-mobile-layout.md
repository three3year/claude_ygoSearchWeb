# 09 — 手機版面

**What to build:** 在手機上查得動——比賽中或組牌時掏出手機能用。範圍是「能用就好」:
側欄在窄螢幕收成頂部可摺疊區、卡片改單欄、圖片縮小。三到四條 media query。

**不做**的事情要一起講清楚,免得範圍膨脹:不做觸控手勢、不做下拉重整、不做底部固定搜尋列、
不做手機專用的條件全螢幕層。oldProject 整份 `style.css` 只有一條 media query,本站做到
四條就已經比它認真。

**Blocked by:** 05 — 卡片參數軸、06 — 效果類型與必發選發軸

**Status:** resolved

- [x] 窄螢幕(720px 以下)側欄收成頂部可摺疊區,預設收起、點一下展開
- [x] 卡片改單欄,卡圖縮小但仍看得清楚
- [x] 條件區的按鈕群、範圍輸入框在窄螢幕不溢出、不需要橫向捲動
- [x] 分頁器在窄螢幕不換行成三四排
- [x] 桌機版面完全不受影響
- [x] 以瀏覽器裝置模擬檢查三種寬度(手機直立、手機橫放、平板)

## Comments

2026-08-14 實作完成。三條 media query(900 / 720 / 430),`web/index.html` 多一顆摺疊鈕
與一層 `.sidebar-body`,`web/js/query.js` 多開合與條件數,`web/js/render.js` 的分頁器
頁碼窗改由 CSS 決定。接縫 3 測試多 4 條(共 74 條);`web/data.js` 不變——這一票沒有動索引。

**分界選在 720,而 900 那條只收窄不改版面。** 平板直立(768〜834)兩欄仍然放得下側欄與
卡片,把它們一起推去單欄的話平板反而比桌機難用——條件永遠在畫面外。所以 900 那條只把
側欄從 268px 收到 216px、留白縮一階,720 那條才是「手機」:單欄、摺疊、卡片改直排。
430 那條是小螢幕手機的再收一階(卡圖 168→144、上下頁只留箭頭)。

**摺疊起來看不見條件,所以鈕面上寫著幾條。** 帶條件的網址在手機上一開就是摺著的,不寫的
話使用者拿到的是一批被篩過、卻沒有任何理由的結果——與「值域漏一碼、某批卡無聲消失」
(ADR-0008)是同一個失效模式。數的是**軸**而不是點亮的鈕:屬性點三顆是一條條件(軸內
OR),寫成 3 會看起來像三道篩子。`Query.count()` 吃的就是 `read()` 吐出來的條件物件,
所以它是純的、測得到,而且加一條條件軸時自動算得到它。

**「現在算不算窄螢幕」JS 一個字都不知道。** 開合只是一個 class 與 `aria-expanded`,
寬螢幕由 CSS 讓它不生效——所以 `search()` 一律呼叫 `Query.collapse()`(手機上收起條件區,
桌機上是空動作),不必在 JS 裡再寫一次 720。同一條規則用在分頁器:窄螢幕要畫幾顆頁碼由
CSS 的 `--pg-win` 決定(桌機 2、手機 1),`render.js` 只是問它。斷點抄一份進 JS 的話,
改了 CSS 之後分頁器會在另一個寬度才變窄,而那是看不出原因的版面錯位。

**搜尋完自動收起條件區。** 不收的話按下搜尋、捲回頂端,看到的是自己剛設好的條件而不是
結果——手機上條件區佔滿整屏。這不是票面「不做」清單裡的手機專用互動(那說的是觸控手勢、
下拉重整、底部固定搜尋列、全螢幕條件層),而是摺疊本身少了就不成立的一半。

**手機版的兩條 sticky 疊在一起:摺疊鈕在 0、搜尋列在 38px。** 桌機版的「搜尋」釘的是側欄
自己的捲動頂端(側欄 `overflow-y: auto`),手機版側欄不再是捲動容器,所以改釘在頁面上、
讓開摺疊鈕的高度。兩條都要有:條件一長串,捲到種族那一排時「收起來」與「搜尋」都還在
手邊。實測 `[0,38]` / `[38,100]`,不重疊。

**iOS 的輸入框放大是「不需要橫向捲動」真正的殺手。** Safari 對 `font-size` 小於 16px 的
輸入框在聚焦時會自動放大整頁,而放大之後版面就橫著捲了。手機版因此把側欄的輸入框與
選單一律拉到 16px;三態鈕也一併加大到 30px 高(手指不是滑鼠指標)。

### 驗證方式:CDP 裝置模擬(拋棄式,不進 repo)

票面最後一項要的「瀏覽器裝置模擬」用 headless Chrome + CDP 真的跑過,不是目測 CSS:
node 24 內建 `WebSocket`,`Emulation.setDeviceMetricsOverride` 給真的 390/360/844/820/1440
視埠(`--window-size` 不行——Chrome 在 Windows 上有 500px 的最小視窗寬,量出來的 `innerWidth`
永遠是 500,而那正好落在 430 與 720 之間、看起來「好像有生效」)。零安裝原則不受影響:
工具在 scratchpad,repo 裡一個檔都沒加(ADR-0007 擋的是 Playwright 那種進 package.json
的依賴)。實測結果:

- **五種寬度橫向溢出全部為 0**(`scrollWidth - clientWidth`),而且逐一掃過 body 底下每個
  元素、沒有任何一個的右緣超出視埠。條件區展開時另測一次——收著的時候它是 `display: none`,
  第一輪根本沒量到,而「按鈕群與範圍輸入框不溢出」問的就是展開的那個狀態
- **分頁器 285 頁在 360px 上只有一排**:第 1 頁是 `‹ 1 2 … 285 ›`、第 284 頁是
  `‹ 1 … 283 284 285 ›`,連跳頁框都在同一排
- 摺疊鈕只在 ≤720 出現(390/360 是 `flex`,844/820/1440 是 `none`),開站時條件區收著
- 卡片在 390/360 是直排、卡圖 144px,在 844/820 是橫排、卡圖 150px,桌機 180px
- 點摺疊鈕 → `aria-expanded` 與 class 同時翻;設兩條條件按搜尋 → 收起、鈕面寫「篩選條件・
  2 項」、17 張結果、網址照樣寫得進去

**「桌機版面完全不受影響」是逐元素比出來的,不是看起來一樣。** 把 HEAD 的 `web/` 複製一份
當對照組,同一個瀏覽器工作階段裡在 1440 / 1100 / 901 各載入兩份,比 body 底下**每一個元素**
的 x/y/寬/高:1,085 個元素、**位置差異 0 處**。(卡圖關掉——CDN 什麼時候載完不是版面的
一部分,留著會讓兩張截圖必然不同。)

這一比抓到一個真的回歸,已修:留白原本從 `.sidebar` 搬進了新的 `.sidebar-body`(為了讓
摺疊時留白跟著收掉),而 sticky 貼齊的是**捲動容器的 padding 邊**——桌機的「搜尋」那一條
因此往上跑了 12px。改成寬螢幕的留白留在 `.sidebar` 上、只有手機版搬進內層。目測絕對看不到
這 12px,而它就是「完全不受影響」與「幾乎不受影響」的差別。

DOM 那一側另以拋棄式冒煙對過(最小 DOM stub + 真實 `data.js`,先例是票07/08):開站是收著
的、點兩下開了又關、設條件按搜尋後收起且鈕面寫著 2 項、清除條件後數字回到沒有、
`--pg-win` 從 2 換成 1 時分頁器真的少畫幾顆(7 → 5)。
