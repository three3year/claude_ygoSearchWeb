## 需要你決定的

### 白名單是哪幾種動作?

決定(2026-11-03):(a)9 種:リリース、除外、重ねる、送る、戻す、捨てる、取り除く、見せる、払う。與效果位不同:效果位不過白名單,每個述語錨點都出框;這裡只出白名單內的。

手續步驟共 17 種動作(337 步);票 01 Q10 已排除 存在、になる、となる、合わせる、異なる、P召喚可能。剩 11 種,其中兩種是單卡怪例。

- (a)9 種(建議):リリース、除外、重ねる、送る、戻す、捨てる、取り除く、見せる、払う——283 框、271 張。発動 只有 13567610 一步,寫的是「相手が…発動していた場合」,是前提、做的人是對手,施事者一律 自分 會錯;選ぶ 只有 38082437(Ｄ・テレホン)一步,那句其實是效果文被誤認成召喚條件。
- (b)11 種,連 発動、選ぶ 也出:285 框。代價:這兩框的施事者與位置都是錯的。

### 解析錯誤是修抽取,還是只靠白名單擋?

決定(2026-11-03):(a)本規格不先修;LLM 抽驗列出的抽取錯在抽驗票逐卡修、複檢。同效果位歷來的抽驗做法。

白名單擋得掉的只有雜訊動作(10000 的「10000以上になる」)。擋不掉的是動作對、論元錯的步驟,目前看到 10000080(ラーの翼神竜－球体形)第二步:對象抽成「召喚または相手フィールドのモンスター3体」、目的抽成 自分フィールド(那是召喚到的地方)。

- (a)本規格不先修;304 張 LLM 抽驗列出的抽取錯,在抽驗票逐卡修、複檢(建議):和以往各線的抽驗做法一樣,錯有多少由抽驗量出來。
- (b)實作票先修 10000080 的「、または」切分。代價:只修已知的一張,其餘仍靠抽驗。

### 「1体ずつ」這類手續數量要不要另補?

決定(2026-11-03):(a)不另補。同效果位:片語取子句數量的規則不改。

手續句含 ずつ 的 21 框。走完整條結構化後,16 框的受事者片語已從子句取到數量(1体ずつ、2体ずつ、1枚ずつ),3 框本來就有 N種類,只剩 2 框(46186135、48658295:「それぞれ１体ずつ、上記のカードを」數量寫在受事者前面)沒有。

- (a)不另補(建議):與效果位同一套片語規則,沒有專給召喚手續的例外。
- (b)補這 2 框:要改片語取子句數量的規則。代價:會動到效果位的既有框,另要驗。

### 召喚來源沒寫時,此卡算在哪?

決定(2026-11-03):(a)依卡種:寫了召喚來源照寫;沒寫時主牌組怪獸算手牌、額外牌組怪獸算額外牌組。與效果位不同:效果位的發動位置依序看句中寫明、觸發事件、此卡自己移動,都沒有才預設場上;召喚手續框只看召喚來源。

票 01 Q12 定了動作對象把此卡當成在召喚來源的區域判定。召喚手續框 283 個裡 208 個所屬的召喚條件沒寫來源(只寫「特殊召喚できる」):額外牌組怪獸 117、主牌組 91。

- (a)依卡種(建議):主牌組怪獸算手牌、額外牌組怪獸(融合、S、X、連結)算額外牌組;寫了來源的照寫。和「只用寫了的來源、沒寫照現行預設場上」比,判定差 33 框(皆非 → 非此卡 27、非此卡 → 非此卡(理由改)4、非此卡 → 皆非 2)。例:「自分フィールドのモンスターを全てリリースした場合」照場上會算含此卡,依卡種算非此卡。
- (b)沒寫照現行預設場上。代價:召喚前此卡不在場上,上面那類全部類會判成含此卡。
- (c)沒寫當區域不明。代價:全部類只能在其餘條件都對得上時判可能含此卡,大多停在皆非。

### 「重ねる」沒寫主題時,動作對象算不算此卡?

決定(2026-11-03):(a)召喚手續的 重ねる 一律算此卡。與效果位不同:效果位的 重ねる 照現行受事者規則判(主題、對象寫此卡才算)。

超量疊放的手續 68 框,被疊上去的一定是要召喚的這張。照現行動作對象規則,寫了「このカードは」的 33 框算此卡(主題是此卡 32、受事者是此卡 1),沒寫的 35 框算皆非(沒有受事者 31、全部類區域不明 3、屬性沒有主人 1)。

- (a)召喚手續的 重ねる 一律算此卡(建議):動作對象選「此卡」時 68 張超量的疊放手續都查得到。
- (b)照現行規則。代價:同一種疊放手續,有沒有寫主題判得不一樣。

### 效果位 0 張時的後備位置要不要排進召喚手續?

決定(2026-11-03):(a)後備順序 代價、條件、召喚手續。同現行後備規則,只是多排一個位置在最後。

現行規則:新標籤位置預設 效果;效果位 0 張時依序取 代價、條件 第一個有張數的。實算:目錄 237 個具名查詢有 26 個在召喚手續有張數,沒有一個效果位是 0 張,所以現在不論怎麼選,畫面都一樣(見 [Further Notes](<#Further Notes>))。

- (a)排在後備的最後(建議):規則統一成「效果 0 張取第一個有張數的位置」;以後若有只在召喚手續有張數的列,標籤不會是 0 張。
- (b)不排進後備:召喚手續一律要自己按亮(Q3 的字面)。代價:上面那種列加出來的標籤是 0 張。

## Problem Statement

站主想查「黑魔導從場上到除外」,毀滅的黑魔術師(滅びの黒魔術師)不在結果裡。它的除外寫在召喚條件「自分フィールドのレベル６以上の魔法使い族・闇属性モンスター１体を除外した場合のみ特殊召喚できる」,這句被認成約束框架,手續只存成原始字串,不出動作框架,動作搜尋看不到。全語料 304 張卡的召喚條件帶手續(解放、除外、疊放、送墓、回牌組…),全部查不到。

## Solution

1. 召喚條件裡的手續步驟,動作在白名單內的,各出一個動作框架,位置是新的第四個值**召喚手續**。約束框架照舊記手續,逐位元組不變;召喚條件本身的「特殊召喚できる」仍不出。
2. 召喚手續框走完整條結構化:片語、區域、施事者、方式、否定形、回指、動作對象。兩條專門規則:施事者一律 自分;動作對象把此卡當成在召喚來源。
3. 匯出檔帶第四個位置,格式版本加一;目錄每列多一格召喚手續張數與雜湊;不開新的目錄列。
4. 述詞沒寫位置就是四個位置都看;「全語料至少命中一張」的合計口徑跟著改成四個位置。
5. 抽屜位置鈕四顆;新標籤照舊預設只看效果,召喚手續要自己按亮。網址照舊,位置值多一個「召喚手續」。
6. 304 張全數 LLM 抽驗。

驗收:加「除外」標籤、位置按亮召喚手續,毀滅的黑魔術師在結果裡,命中句是召喚條件那句;既有框架、約束框架、目錄三個位置的張數與雜湊都不變。

## User Stories

1. 作為使用者,我要查得到「黑魔導從場上到除外」這類寫在召喚條件裡的除外,這樣毀滅的黑魔術師不會漏掉。
2. 作為使用者,我要召喚條件裡的解放、除外、疊放、送墓、回牌組、丟棄、取除素材、給對手看、支付 LP 都查得到,這樣召喚手續和效果裡的同一個動作用同一張標籤找。
3. 作為使用者,我要新標籤預設只看效果,這樣既有查詢的結果不會突然多出一堆召喚條件。
4. 作為使用者,我要在抽屜的位置欄看到第四顆「召喚手續」,自己按亮才算,這樣要不要看召喚條件由我決定。
5. 作為使用者,我要只按亮召喚手續、關掉效果,這樣能專門找「召喚手續要除外墓地的卡」。
6. 作為使用者,我要召喚手續的命中句標出位置,這樣分得出這張卡是效果還是召喚條件中的。
7. 作為使用者,我要召喚手續框的區域和效果框同一套,這樣「除外←墓地」這種具名查詢在召喚手續也照樣成立。
8. 作為使用者,我要召喚手續框的受事者中心詞、數量、修飾語和效果框同一套,這樣中心詞欄、數量欄的條件也能用在召喚手續上。
9. 作為使用者,我要召喚手續的施事者一律是我方,這樣「施事者=自分」的查詢不會漏掉召喚手續。
10. 作為使用者,我要動作對象「此卡/非此卡」把此卡當成在召喚來源判,這樣「自分フィールドのモンスターを全てリリース」不會被當成可能解放到此卡。
11. 作為使用者,我要召喚來源沒寫時依卡種推(主牌組在手牌、額外在額外牌組),這樣多數召喚條件也判得出此卡在哪。
12. 作為使用者,我要超量疊放的手續一律算動到此卡,不論有沒有寫「このカードは」,這樣「此卡被疊上去」的 68 張超量都查得到。
13. 作為使用者,我要「存在する場合」「合計が10000以上になる」這類前提不出框,這樣召喚手續只有真的動作。
14. 作為使用者,我要召喚條件本身的「特殊召喚できる」仍不出框,這樣「特殊召喚」的結果不會多出每一張有召喚條件的卡。
15. 作為使用者,我要述詞沒寫位置時四個位置都看,這樣網址或程式產生的無位置述詞涵蓋召喚手續。
16. 作為使用者,我要目錄樹上顯示的張數照舊是效果位的,這樣我熟悉的數字不變。
17. 作為使用者,我要舊網址照樣讀得進來、查到的卡不變,這樣分享出去的連結不會壞。
18. 作為使用者,我要網址能記「位置:召喚手續」,這樣按亮召喚手續的查詢分享得出去。
19. 作為使用者,我要拆解頁的框架列分得出召喚手續,這樣看卡片拆解時不會把它當成效果。
20. 作為站主,我要既有的動作框架、約束框架逐位元組不變,這樣這次只加不改,以前的驗收都還算數。
21. 作為站主,我要目錄三個位置的張數與卡集合雜湊不變,這樣前端與參考評估器的對拍不必重做三個位置的部分。
22. 作為站主,我要 304 張帶手續的卡全部經 LLM 抽驗,這樣召喚手續框的錯有多少是量出來的,不是猜的。
23. 作為站主,我要抽驗也檢查被白名單擋掉的步驟裡有沒有真的動作,這樣白名單不會漏收。
24. 作為站主,我要匯出檔的格式版本加一、網站建置檢查新版本,這樣舊的建置程式讀到新檔會明確失敗。
25. 作為站主,我要參考評估器與 JS 評估器在四個位置上都對得上,這樣召喚手續的查詢結果兩邊一致。
26. 作為站主,我要建置報告與分詞報表把召喚手續列成一欄,這樣框數的分佈看得到。
27. 作為站主,我要「全語料至少命中一張」改看四個位置,這樣目錄的保留規則和查詢語意一致。

## Implementation Decisions

**位置值域**
- 新增第四個位置值「召喚手續」,接在 代價、效果、條件 之後。順序要放最後:索引把位置編成值域序 + 1,接在最後既有的 1〜3 不變。
- 參考評估器、匯出、目錄張數、建置報告、拆解頁資料都從同一個位置清單取值,多一個值自動帶到;只寫死三個位置的地方逐一改(動作對象的發動位置、施事者預設、片語報表那一行、拆解頁樣式)。

**分詞鏈(約束框架與框架抽取)**
- 召喚條件規則已經把手續步驟的述語錨點收在待處理清單裡;改成:動作在白名單內的錨點,不再被召喚條件的吃掉範圍蓋住,照一般錨點出動作框架,位置標召喚手續(不經代價/效果/條件的判定)。白名單外的錨點照舊被吃掉。
- 白名單是一份封閉表,9 種:リリース、除外、重ねる、送る、戻す、捨てる、取り除く、見せる、払う,比對抽取時的動作名(発動、選ぶ 與 Q10 排除的前提不在表內)。
- 約束框架照舊:形式、方式、手續、來源欄都不變;手續欄不改成指向動作框架。召喚條件本身的召喚錨點不出框架。
- 召喚手續框照一般框架走第四版論元全程:片語結構化 → 回指 → 區域、施事者、方式、否定形、回指回填;詞元正規化照舊。框架依原文順序和其他框架混排。

**兩條專門規則**
- 施事者:位置是召喚手續的框架,施事者一律 自分,來源記 預設、標推得;不看主題與主語(「このカードは…をリリースして」的主題 このカード 不是施事者)。施事者來源的封閉表不加新值。
- 動作對象:召喚手續框的發動位置是所屬召喚條件的召喚來源——寫了來源照寫的區域;沒寫時主牌組怪獸 手牌、額外牌組怪獸(融合、S、X、連結)額外牌組,發動位置來源另記一個值(寫明的召喚來源/推得的召喚來源),建置報告分項列。同一句的其他框架的發動位置照現行規則。召喚手續框不算此卡自己移動,不改後面框架的發動位置。
- 重ねる:位置是召喚手續的 重ねる 框,動作對象一律 此卡,理由另記一個值(召喚手續的疊放),不走受事者判定。

**匯出檔與參考評估器**
- 框列的位置值多一個「召喚手續」;值域照位置清單匯出。
- 目錄每列的張數與雜湊各多一格召喚手續;大類、中類列是底下具名查詢的聯集,同樣多一格。這是票 01 Q14「目錄每列多一格」的讀法:資料多一格,目錄樹畫面照舊只顯示預設位置(效果)的張數。
- 「全語料至少命中一張」改成四個位置任一有張數;實算沒有列因此留下或刪掉。
- 統計的位置分項多一格。格式版本 2 → 3,網站建置的版本檢查跟著改。
- 參考評估器的語意不變:述詞沒寫位置 = 值域裡的每個位置都看(現在是四個)。

**網站建置與前端**
- 索引的位置編碼照值域序,召喚手續是 4;不改編碼方式。
- 條件模型:新標籤位置預設照舊 效果;效果位 0 張時的後備順序改成 代價、條件、召喚手續。抽屜位置欄從值域來,自然是四顆;「至少留一個」規則照舊。
- 標籤短句、命中句的位置前綴照現行規則(非預設位置顯示「召喚手續:」)。網址格式不變。
- 目錄樹的張數、灰字規則照舊用預設位置,不另顯示召喚手續張數。

**拆解頁與報表**
- 拆解頁的框架列給召喚手續自己的樣式與圖例,不再落到效果的樣式。
- 分詞報表、建置報告、目錄命中報表凡是逐位置列的,多一欄召喚手續;寫死三欄的那一行改成照位置清單。

**LLM 抽驗**

- 錯誤類型:漏出(該出沒出,含被白名單擋掉的真動作)、多出、詞元錯、區域切錯、中心詞或修飾語類錯、數量錯、動作對象錯,另記成因(規則或抽取)。

## Testing Decisions

- 好的測試只看外部行為:給一句卡文看出的框架,給述詞與框列看命中,給標籤看抽屜選項;不測錨點、吃掉範圍這些內部結構。
- **分詞鏈接縫**(既有):一句效果外文本 → 框架清單。例子:滅びの黒魔術師的召喚條件出一個 除外 召喚手續框(來源 自分 場上、施事者 自分、動作對象 非此卡),約束框架照舊;存在、になる 不出;超量疊放出 重ねる、沒寫主題也算此卡;召喚來源沒寫時的發動位置依卡種(主牌組 手牌、額外 額外牌組);「このカードは…をリリースして」施事者是 自分。先例:約束框架與框架抽取的既有單元測試。
- **全語料守門**(既有):剝鍵比對與下游基準(動作對象、回指)在剝掉召喚手續框、框序重編後 0 差異,不重凍;匯出檔剝掉召喚手續框列與新鍵後與現行逐句相同;封閉表外值 0。
- **參考評估器與 JS 評估器對拍**(既有):例子夾具重產(格式版本 3,加召喚手續的例子與值域),兩邊全過;全語料目錄每列 × 四個位置的張數與卡集合雜湊,匯出檔與 JS 重算 0 不符。先例:named-queries 的夾具與 predicate-index 的全語料對拍。
- **條件模型接縫**(既有):抽屜位置欄四顆、新標籤預設效果、效果位 0 張的後備順序、網址「位置:召喚手續」讀寫來回不變。先例:conditions.test.js 的位置例子。
- **LLM 抽驗**:304 張全數,見上。
- **真瀏覽器**:交件票真 Chrome 桌面與手機寬各走一輪:加「除外」標籤、按亮召喚手續,毀滅的黑魔術師在結果、命中句標「召喚手續:」;只按亮召喚手續的查詢貼網址重開不變;console 錯誤 0。
