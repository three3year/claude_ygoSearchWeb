# 04 — 推導方法票:從分詞抽動作框架,產出每張卡的效果拆解

**Status:** ready-for-agent

**Blocked by:** 03(已 resolved;分詞詞典已依 ADR-0014 整理、試點層 OOV 歸零)

## Problem Statement

站主要重新推導[[動作類別]],但現在手上只有每句效果文的詞序列:句型模板 14,418 種、top-100 只覆蓋效果句 6.57%,模板只收斂卡名與數字,幾乎一句一形,讀不出「這張卡在做什麼」的結構。舊效果 Tag 線的教訓是:21 類加槽位丟掉了誰對誰做什麼、做的順序與代價/效果的分界,指標全綠卻沒有用。站主需要一份**每張卡完整、讀得懂的效果拆解**,先拿來分析理解,之後才決定怎麼歸組成類別、要不要上網站搜尋。

## Solution

在試點層(新格式新卡,7,818 張、24,599 句)從[[效果文分詞]]的詞序列,以符號式規則抽出[[動作框架]]:每個動作一個框架,依原文順序排,框架記錄動作(述語詞元)、[[論元]](對象/來源/目的)、位置(代價/效果/條件)與極性(肯定/否定/可能)。一張卡的框架合起來就是它的效果拆解。

驗收分兩段:先以分層抽樣的 300 張卡交給多個 LLM 子代理「看原文與框架挑錯」,依錯誤類型修規則、同批樣本複檢,修到只剩個別長尾;再把**每張卡一頁的拆解**(原文與框架左右對照)交站主質性驗收,附覆蓋率與「已知未修」清單。

## User Stories

1. 身為站主,我想打開任一張卡就看到它每個效果被拆成一串動作框架,以便判斷「讀不讀得出這張卡在做什麼」。
2. 身為站主,我想看到框架依原文順序排列,以便讀出效果的處理流程(先付什麼、再做什麼、之後做什麼)。
3. 身為站主,我想看到每個框架標明位置是代價、效果還是條件,以便分辨「為了發動付出的」與「發動後做的」。
4. 身為站主,我想看到「…場合」「…時」這類觸發句被抽成條件框架,以便知道效果在什麼情況下成立。
5. 身為站主,我想看到每個框架的動作以詞元記錄(送って、送った 都記 送る),以便同一動作的不同活用歸在一起。
6. 身為站主,我想看到框架的對象論元(を 前的詞),以便知道動作作用在什麼東西上。
7. 身為站主,我想看到框架的來源論元(から 前的詞),以便知道卡從哪個區域被移動或召喚。
8. 身為站主,我想看到框架的目的論元(に/へ 前的詞),以便知道卡被移到哪裡。
9. 身為站主,我想看到框架的極性(肯定/否定/可能),以便分辨「破壊する」「破壊されない」「破壊できる」。
10. 身為站主,我想讓「できない」類的否定動作被標成否定,以便耐性與行動限制不會被誤讀成正常動作。
11. 身為站主,我想讓召喚法+召喚(法:特殊|召喚、法:融合|召喚)被當成一個動作,以便召喚類動作有一致的形狀。
12. 身為站主,我想讓サ変名詞+する(破壊|する、除外|する)被當成一個動作,以便動作不被拆成名詞與時態兩截。
13. 身為站主,我想讓列舉前項(魔法(カード)・罠カード)在論元裡顯示補全後的值,以便知道對象是魔法卡或陷阱卡。
14. 身為站主,我想讓指示綁定(このカード、そのモンスター)出現在論元裡,以便看出動作作用在自身還是前文提到的卡。
15. 身為站主,我想讓一句含多個動作時各自成框架,以便「捨てて…加える」不會被壓成一個動作。
16. 身為站主,我想讓卡片的多個效果(①②③、靈擺效果)在拆解頁上分段顯示,以便對照原文段落。
17. 身為站主,我想在拆解頁用卡號或卡名找卡,以便直接檢查我關心的卡。
18. 身為站主,我想在拆解頁看到原文與框架左右對照,以便逐句核對抽得對不對。
19. 身為站主,我想看到一份「抽不到任何框架的句子」清單,以便知道規則的盲區。
20. 身為站主,我想看到框架覆蓋率(有抽到動作的句子比例)當儀表板參考,以便追蹤進度,但不拿它當通過門檻。
21. 身為站主,我想在交件前讓 LLM 子代理先挑過一輪錯,以便我驗收時不用看到大量已知的高頻錯誤。
22. 身為站主,我想讓 LLM 檢驗用分層抽樣的固定 300 張卡(單效果怪獸、多效果、魔陷、靈擺),以便問題能代表整體且複檢可比。
23. 身為站主,我想讓 LLM 回報的錯誤附理由並分類(漏抽動作、論元抽錯、位置判錯、極性判錯),以便知道該修哪一類規則。
24. 身為站主,我想讓規則修正後用同一批樣本複檢,以便確認修正有效且沒有改壞別處。
25. 身為站主,我想在交件時拿到「已知未修」清單,以便知道剩下的長尾是什麼、為什麼沒修。
26. 身為站主,我想讓抽取結果決定性(同輸入重跑逐位元組相同),以便規則改動的影響可以逐句比對。
27. 身為站主,我想讓每次規則修正都附一句回歸例子進測試,以便之後的修改不會把已修好的句型改壞。
28. 身為站主,我想讓框架抽取與分詞鏈一起重跑,以便詞典改動後拆解自動更新。
29. 身為維護者,我想讓框架的資料格式有清楚的欄位定義,以便下一張票(類別歸組)直接拿來用。
30. 身為維護者,我想讓這張票不碰舊效果 Tag 資料,以便新推導不被舊線的問題帶偏。

## Implementation Decisions

- **新增框架抽取模組**,與分詞鏈同一處(試點期都在 `.scratch/effect-tokenize/`):輸入一句效果文原文與同卡同段上文,內部呼叫既有分詞器與詞典取得詞序列,輸出動作框架清單。框架抽取是分詞鏈的下一步,讀分詞結果、產出框架建置產物(決定性、不入版控,與 tokens.json 同待遇)。
- **述語錨點**:動作由述語決定——動詞(含活用形,以詞典 lemma 欄歸詞元)、サ変名詞+する 家族(破壊|する、除外|された)、召喚法+召喚(法:特殊|召喚)、名詞+できる/できない。述語的詞元就是框架的「動作」值。
- **論元規則**:從述語往前、在同一子句內依助詞收論元——を=對象、から=來源、に/へ=目的。論元值保留該位置的詞(含指示綁定、列舉前項補全值、數量約束、卡名佔位)。第一版只收這三個論元;主體(が/は)、數量、連接(その後/並列)、期間(ターン終了時まで)留到第二版。
- **子句切分**:一句依句讀與接續(。、て形、し、場合/時 等)切成子句,一個子句至多一個述語錨點;多述語的子句依接續再拆。具體切分規則在實作中隨 LLM 檢驗收斂。
- **位置判定**:沿用[[槽位]]既有「位置」的判準(發動子句裡的付出是代價、處理段的動作是效果),另加「條件」值給「…場合/…時」觸發句與發動條件。發動子句以「発動できる/発動する」為界。
- **極性**:述語後接 ない/されない/できない 系為否定,できる 系為可能,其餘肯定。
- **框架資料格式**(第一版欄位):卡號、效果段落位置、句序、框架序、動作(詞元)、對象、來源、目的、位置、極性、對應的詞序列範圍(供拆解頁標原文)。
- **拆解頁**:檢視頁新增「卡片拆解」分頁——依卡號/卡名找卡,左原文(依段落)右框架表;另一分頁列「抽不到框架的句子」與框架覆蓋率。沿用檢視 artifact 的發布方式。
- **LLM 檢驗流程**:依效果數與卡種分層、固定種子抽 300 張(約單效果怪獸 100、多效果 100、魔陷 70、靈擺 30),切成 6–8 份交給 LLM 子代理,每份讀原文與框架,回報錯誤(漏抽動作/論元抽錯/位置判錯/極性判錯)附理由。錯誤依類型歸納、修規則、同批複檢,直到剩個別長尾;樣本清單與每輪錯誤歸納存檔以便複檢比對。
- **術語**:新欄位稱[[論元]],不沿用舊[[槽位]];「位置」沿用並加「條件」值。CONTEXT.md 已新增[[動作框架]]與[[論元]]詞條。
- 粒度依 ADR-0014:術語身份不在詞典,框架是推導層組回術語的地方(例:墓地|へ|送る 的框架為 動作=送る、目的=墓地)。

## Testing Decisions

- **唯一接縫**:「一句效果文原文(帶同卡同段上文)→ 動作框架清單」。測試使用真的分詞器與詞典,只斷言輸出框架的動作、論元、位置、極性,不測規則內部怎麼寫。
- 好的測試是句型層的回歸例子:一句原文、預期的框架清單。每次修規則(含 LLM 檢驗後的修正)先補一句會失敗的例子再修。
- 第一批例子涵蓋:單動作檢索(デッキから…手札に加える)、代價+效果(…捨てて発動できる。…加える)、條件框架(…場合に発動できる)、否定(戦闘では破壊されない)、召喚法(墓地から…特殊召喚する)、列舉前項論元(魔法・罠カード を破壊する)、その後 連接的多框架。
- 測試寫法沿用專案既有的 unittest(test_*.py 放在模組旁),先例是 script/tag_card/test_tag_line.py 這類以句子為輸入、斷言抽取結果的測試。
- 詞典改動可能連帶影響測試,屬預期:測試失敗時判斷是框架規則還是分詞慣例該改。

## Out of Scope

- 框架歸組成類別(取代 21 類的新分類表),另開票。
- 網站搜尋介面與前端索引的任何改動。
- 第二版論元:主體、數量、連接、期間、對象決定方式(対象として/選んで/ランダム)。
- 試點層以外的語料(新式全量),方法成形後另開票擴展。
- 舊效果 Tag 資料(`tag_cards.json` 的 tag、規則層、遮蔽測試),完全不用、不對照。
- LLM 獨立抽取再比對的檢驗方式(本票採「看框架挑錯」)。

## Further Notes

- 驗收依 spec「量化參考、質性為準」:框架覆蓋率與 LLM 錯誤數是儀表板,通過與否由站主翻拆解頁裁定。
- LLM 檢驗的子代理數量在中等規模(6–8 個);若要用多代理工作流程編排,需站主明確同意。
- 2026-10-09 站主確認實作期間的四項偏離保留:「〜を対象として」成條件框架(動作 対象とする,原 Out of Scope 的「對象決定方式」只剩 選んで/ランダム 留第二版)、「〜となる/〜と同じになる」的 と 補語收為目的、LLM 檢驗錯誤類型加第五類「多抽(不是動作)」、同批複檢之外另以新種子抽驗。「〜したターン」一律抽成條件框架(発動 專例除外)。
- 2026-10-08 grill 定案:用途=分析理解、產物=動作框架、抽取=述語錨點+助詞論元規則、欄位=核心先行、驗收=LLM 挑錯後每卡一頁、舊 tag 完全不用、類別歸組另開票、論元另立新詞。
