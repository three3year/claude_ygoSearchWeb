# 02: 候選卡計算加速

Status: resolved

**What to build:** 物件條件式的候選卡(卡片總表裡滿足條件式的卡)算得夠快,讓之後「建置時把全部候選卡算好」不會拖垮建置時間。結果一張都不能變。

- 先把卡片總表按屬性、種族、等級、字段等建好索引,多數條件式不必逐張掃。
- 只改算法,不改判法:每個物件在每條對象線上的候選卡,加速前後完全相同。
- 這是重構前的準備工作;攤平(票 03)與索引建置(票 06)都建在它上面。

- 規格:需要你決定的「Q13」;實作決策「建置與門檻」。
- 背景數字(不是驗收數字):照原型的算法逐張掃,全庫約 10 分鐘;卡片結構建置約 23 秒。

**Blocked by:** None (can start immediately)

## Comments

### 實作(2026-11-23)

- 新模組 `script/action_structure/candidate_cards.py`:`CandidateCards(cards, structures).of_line(owner, line)` 回傳一條對象線上物件的候選卡(卡片總表條目,照總表順序)。判法仍是 `action_query` 的 `card_fits` / `eval_condition`,只改算法:
  - 索引:卡名、setcode、大類(取卡片屬性表每一列,不看位置條件)與屬性比較用到的屬性值,先取一個「一定包含全部答案」的候選池,只對池裡的卡判。
  - 拆項:且 = 各項判 True 的卡取交集、或 = 取聯集;各項分開算、分開記;每張卡都判 True 的項(表側表示、自分フィールド…)從且裡拿掉,「モンスター１体」與「表側表示のモンスター１体」共用一份答案。
  - 共用:答案照判法讀得到的東西記住(條件式、條件式用到的名稱字面、「從」落在哪些「有列帶位置條件」的區域)。
  - 引用:含引用的物件仍逐張判 `card_fits`,但被引用物件的候選卡先去掉「代入結果一定相同」的(判法從被代入的卡讀到的值相同),並照異同 相同 的每個屬性篩;被引用物件都不是此卡、不再含引用時,答案也共用。
- `action_query.py` 只加了 `CardView.rows()`(把卡名、setcode、大類的列交給索引),`run_query` 與建置第二輪(`resolve_references`)的路徑沒有改。
- 測試 `test_candidate_cards.py`(23 個):字段、卡名的位置條件、等級/階級/連結值、種族屬性、攻擊力「？」、子類型、字段子系列旗標、卡名包含、或、非、狀態、此卡、引用、同族不同名、多屬性相同、判不了的原子,以及同一份 `CandidateCards` 跨卡共用時名稱表、被引用物件、「從」各不相同的情形。

### 全庫比對

- 方法:同一份 `data/action_structure.json`(現行產物)與 `data/cards.json`,走過每張有結構的卡、每個區塊(含內嵌效果)的每一段、每條帶物件的對象線,共 **44,517 條線**,各輸出一行「卡號、段 id、線序、候選卡號(照總表順序)」。
  - 加速前:改動前的程式碼快照,逐張掃整份總表判 `card_fits(entry, 物件, 卡, 名稱表, 這條線的「從」)`。同樣的物件只算一次,去重鍵取 `card_fits` 讀得到的全部(物件的 unparsed、kind、count、source、條件式、名稱字面、「從」;此卡、子集、含引用時再加卡號與物件 id),實際算了 24,889 次。
  - 加速後:每條線各呼叫一次 `CandidateCards.of_line`(不另外去重,共用由模組自己決定)。
- 結果:兩份輸出逐行相同,**44,517 條線差異 0 條**;候選卡合計 124,262,858 張次,沒有候選卡的線 4,335 條。加速後跑兩次輸出也逐位元組相同。
- 既有測試:`python -X utf8 -m unittest discover -s script/action_structure` 944 個全綠(含新加的 23 個)。
