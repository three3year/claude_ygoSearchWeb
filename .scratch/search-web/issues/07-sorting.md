# 07 — 排序

**What to build:** 結果的順序變得可理解、而且「最高攻擊力的暗屬性怪獸是哪張」答得出來。

預設是**領域序**,沿用 oldProject `cmpCards` 的七層比較:大類 → 靈擺卡排後 →
[[卡片子類型]]序 → 等級/階級/連結值**高到低** → 屬性序 → 種族序 → [[卡片密碼]]升序。
第 3、5、6 層的序**直接取自[[值域正典]]的宣告序**,不另抄一份——oldProject 的
`RACES = VOCAB.race.map(e => e.zh)` 旁註著「與宣告序同一份」,就是這個做法,第三抄因此
不存在(ADR-0008)。

另提供排序選單切換到單鍵排序。

**Blocked by:** 02 — 完整卡片呈現

**Status:** resolved

- [x] 預設七層領域序,同類卡聚在一起、高等在前
- [x] 領域序的比較序取自 `window.VOCAB` 的宣告序,程式裡沒有第二份順序表
- [x] 排序選單:攻擊力、守備力、等級階級、卡名、[[卡片密碼]],各可升降序
- [x] 排序切換不重跑搜尋(只重排已有結果),分頁位置歸 1
- [x] 空值(非怪獸沒有攻擊力、`?`)在數值排序中的位置一致且不會插進數值之間
- [x] 接縫 3 測試:領域序與各排序鍵的順序正確、升降序對稱、排序穩定
      (相同鍵值的卡順序不隨執行變動)

## Comments

2026-08-14 實作完成。新增 `web/js/sort.js`(純模組,不碰 DOM、不讀查詢條件),
`web/index.html` 的 actions 列多一個排序選單與方向鈕,呈現層多一份排序狀態。
接縫 3 測試多 13 條(共 62 條);`web/data.js` 不變——這一票沒有動索引。

**第 1 層也取自宣告序,不只票面寫的第 3、5、6 層。** 大類的順序(怪獸→魔法→陷阱)
同樣是[[值域正典]]的宣告序,沒有理由只有這一層手抄。四個值域(大類、子類型、屬性、
種族)因此全部走 `Util.codesOf`,`sort.js` 裡一張順序表都沒有。對照組是 oldProject:
它的 `RACES` / `ATTRS_ORDER` 由 VOCAB 導出,但 `kindOrder` 與 `SPELL_SUB_ORDER` 仍是
手抄的第二份——在正典裡把儀式移到融合前面,那兩份不會跟著動,而畫面上的順序與按鈕的
順序會從此對不起來,不報錯也不白屏。

**第 3 層比的是「卡框」,而卡框取值域的第一個分組。** [[卡片子類型]]一張卡帶多個碼
(融合效果怪獸的 `s` 是「效果＋融合」),要決定它跟誰站在一起。規則兩條:只看**第一個
分組**(怪獸側的「卡框」;魔法/陷阱側沒有分組,全體都是卡框),多個卡框碼時取**宣告序
最後**的那一個。前者擋的是協調同步怪獸——協調是「能力」組的成員,拿它來排的話那張卡會
從同步那一團裡被抽出來、排到卡通後面去;後者是因為通常與效果不會並存、特殊召喚法的卡框
彼此也不會並存,所以「最後一個」就是那張卡的卡框。靈擺碼在這一層被排除,因為第 2 層
已經把靈擺整批挪到後面了,第 3 層要問的是這張靈擺卡是哪一種卡框(靈擺融合與靈擺通常
不該併成一團)。真實索引上驗過:14,207 張**沒有一張**落在「沒有卡框」那一格。

**空值一律殿後,升序降序都是。** 攻守的空值有兩種來源——非怪獸根本沒有那個欄位、
`?` 是負的哨兵值——**兩種都不是數值**。`?` 當 0 排的話,83 張攻擊力未知的怪獸會混進
攻 0 那一團裡,而那是一個看不出來的錯。反過來讓空值跟著方向翻的話,「攻擊力升序」的
第一頁會是 5,010 張沒有攻擊力的卡,而使用者要的是攻 0 的怪獸。

**等級這個鍵只認 `lv`,連結怪獸在它上面是空值。** LINK-3 是連結值,是另一個參數
(欄位的有無由大類與[[卡片子類型]]決定,見 CONTEXT.md「前端索引」),把它當等級 3 排
就是把兩個值域混成一個。領域序的第 4 層仍然吃 `lk`——那一層問的是「這張卡的規模」,
而排序選單問的是「等級是多少」,兩個問題不一樣。

**升降序對稱的定義:方向連決勝的卡片密碼一起翻。** 有值的那一批與空值的那一批各自
反轉,兩批的前後關係不變(空值永遠在後)。決勝一律落到[[卡片密碼]],而密碼是唯一鍵,
比較函式因此是**全序**——排序結果不靠 `Array#sort` 是不是穩定排序,輸入順序也影響
不了它(測試拿反轉過的輸入排一次,結果逐項相同)。

**卡名比的是碼點序而不是 `localeCompare`。** 後者的結果隨環境的 ICU 版本與 locale 而變,
同一份資料在兩台裝置上會排出不同的順序,而票08 要分享出去的網址講的就是「同一個查詢在
你那邊也長這樣」。

**排序住在呈現層而不是查詢條件裡。** 換一個排序鍵不會改變命中哪些卡,所以它是「怎麼看
這份結果」而不是「要哪些卡」,與分頁同一類。「排序切換不重跑搜尋」因此是結構上成立的:
重排走的是 `View.render()`,根本沒有經過引擎。換鍵時分頁位置歸 1——上一次翻到第 37 頁,
換成攻擊力降序之後留在第 37 頁的話,使用者看到的是「攻擊力最高的卡」以外的任何東西。

**領域序的比較鍵算一次就存起來(WeakMap)。** 比較函式要跑 O(n log n) 次,全表排序時
是二十萬次;每次都重算四個值域的名次要 55 ms,存下來是 11 ms,而分頁每翻一頁都會重排
一次。索引是唯讀的建置產物、卡片物件不會變,所以這份快取不會過期。

**選單的選項由 `Sort.KEYS` 生成,HTML 只留一個空的 `<select>`。** 排序鍵、中文名與
**切換到該鍵時的預設方向**是同一份宣告——選了攻擊力就該看到最高的那張,不必再點一次
方向。分成兩份的話,加一個排序鍵會變成「選單有這個選項但排序沒反應」。領域序沒有方向,
方向鈕在它身上收起來:把七層比較反過來排出來的東西(陷阱在前、等級低到高、密碼大到小)
不對應任何一個問題。

**沒有加 DOM 測試**(spec 的 Testing Decisions:DOM 渲染走人工驗收)。可測的形狀是純的:
`Sort.sort` 吃的就是接縫 3 的回傳形狀,所以測試跑的是「查詢 → 排序」這條真實的路徑。
呈現層另以帶快取的 DOM stub + 真實 `data.js` 冒煙對過五件事:選單的選項由 KEYS 生成、
方向鈕只在有方向的鍵上出現、換鍵重排且回到第 1 頁而總筆數不變(沒有重跑搜尋)、方向鈕
切得動、外部呼叫 `View.setSort` 時選單跟著動(票08 從網址還原條件會走這一條)。
