# 動作搜尋在建置期攤平成動作索引,網站只比對

[[動作搜尋]]的查詢判斷原本直接讀巢狀的[[卡片結構]](50 MB 的 JSON、一千行左右的 Python)。要放上查卡網站時有三個條件同時成立:網站是靜態的,要能雙擊開啟、也要能放 GitHub Pages(ADR-0007),瀏覽器裡跑不了 Python;卡片結構的覆蓋還在提高,每一輪規則回合都會出現新形狀;站主不要因為規則補了新形狀就得一直改搜尋。

因此**建置時由 Python 把卡片結構攤平成[[動作索引]]**:每條[[對象線]]一列(沒有線的段以段為一列),每一欄都是已經解讀完的值——上位詞展開好、子區域算進上位區域、沒寫誰的主動句記成我方、[[不限定]]另外標出。[[物件]]的條件式在建置時對卡片總表求值,換成候選卡集合,壓縮後存。解讀卡片結構的程式只有攤平這一處;Python 的查詢判斷與網站的 JavaScript 都只比對列。動作索引是獨立的 `.js` 檔,和[[前端索引]]分開,使用者第一次打開動作搜尋才載入。

## Considered Options

- **只留 Python,本機開查詢伺服器**:規則改了前端不用動。但上線的站沒有動作搜尋,雙擊開啟也不能用,同一個站兩種開法行為不同,等於推翻 ADR-0007。
- **只留 Python,預先算好所有查詢結果**:動作詞、區域、誰、原因、各開關再乘上一萬多張指定卡,組合算不完。改成每一欄各自算好、網站取交集則會錯:條件必須落在同一段、同一條線上,分開算會把寫在不同段的「從墓地」和「除外」湊成「從墓地除外」。
- **用 JavaScript 把查詢整份移植**:解讀巢狀結構的程式變成兩份,規則每補一種形狀兩份都要改;50 MB 的結構也送不進瀏覽器,要瘦身就得先定一套格式——那套格式就是索引。
- **先把規則補到某個門檻,再做搜尋**:到全覆蓋之前新形狀照樣會出現,改動只是延後;這段期間站上沒有動作搜尋,補規則的先後也沒有實際查詢可以參考。
- **先凍結卡片結構的形狀,再做搜尋**:已經知道有新形狀要加(重複範圍、指回前面那次召喚),每次都得解凍;規則作者也容易把新的意思硬塞進舊欄位。
- **攤平成索引,網站只比對**(採用):規則補新形狀時只改攤平;網站只在新增查詢欄時才要改。

## Consequences

- 比對邏輯有兩份(Python 與 JavaScript),都只比對列。兩份的一致靠測試守:同一份索引、同一批查詢,兩邊命中的卡必須相同;這組測試讓動作搜尋的 Python 測試需要 node。
- 攤平是唯一懂卡片結構的地方。新的查詢欄要先在攤平加欄,索引的格式因此會隨查詢欄成長,不會隨規則成長。
- 候選卡在建置時算好,所以卡片總表或卡片結構一變,動作索引就要重建;效果對應用到效果標記表(效果句的日文原文)與前端索引(效果句的序號),這兩份變了也要重建。
- 動作索引的體積與建置時間各有門檻(8 MB、整個建置 2 分鐘),超過時建置失敗或停下來由站主決定。原型量到的索引是 4.64 MB、傳輸量 1.23 MB。
- 「只給條件」在網站上只開放幾種簡單的條件(大類、屬性、種族、等級、字段、卡名包含),因為網站要自己算出滿足條件的卡,再和候選卡取交集。
- 網站看不到卡片結構,所以玩家介面標得出命中的是哪個[[效果句]],標不出是哪幾個字;日文原文與命中的段留給進階模式另外載入。
