# 每一條待判效果句都必須經 LLM 判定一次,規則只做影子驗證

判定[[效果類型]]時,[[官方明示]]覆蓋約 63% 的[[效果句]],其餘約 8,200 條需要 LLM 逐條判定。判定過程中會不斷歸納出新的分類規則,而這些規則理論上可以直接覆蓋尚未判定的效果句、省下將近一半的工作量。我們**不這麼做**:新規則只寫入 `rule_predicted` 影子欄位,不寫 `kind`;該行仍照常送 LLM 判定,判完當場與影子預測比對,一致則 `source` 升為 `llm_then_rule`,不一致則進衝突清單。

## Considered Options

- **規則覆蓋即跳過判定**(約 12–15 張判定票):工作量少近一半,但歸納出的規則從未被獨立驗證過——一條寫得太寬的規則會靜靜地誤標數十到數百行,而且因為那些行從未被人看過,誤標只能等使用者事後逐卡回報才會浮現。前一世代正是這個失效模式。
- **所有效果句都判定一次**(20 張判定票,採用):每條規則都有一次獨立判定作對照,規則寫錯會在下一票就炸出衝突,而不是等全部跑完。

注意本決定的對象是**歸納出的規則**,不含[[官方明示]]——官方權威資料直接採用、不送判定,這是判定量從 21,947 降到 8,191 的原因。

### 修訂(票52,2026-08-10):「判定一次就算數」是重跑不覆蓋,不是判錯了也不能改

`_merge_clause()` 對 `llm` / `llm_then_rule` 的行一律沿用既有值,再判一次只會進 `judgment_overridden` 清單。這條規矩的對象是**重跑**——建置管線不得把人的成果洗掉。但它把「規範改版後回頭修錯判」也一起擋掉了:規範文件是逐票長出來的(票07 的循環),先判的票用的是還沒補上那一條的規範,同一個句型因此會出現兩個答案(票52 的裝備卡破壞替代句:票13 判永續、票18 判無種類)。剩下的路只有手改 `data/tag_cards.json` 標 `manual`,那等於繞過三道關卡與稽核軌跡。

改判因此走判定票的同一條路,加三道限制:

- **要一張自己的票。** `make_batches.py --rejudge <密碼>:<section>:<index>` 逐條指名標的並產生批次檔(標的必須是已經判過的行),結果檔進 `.scratch/tag-card/judgments/`,稽核軌跡與其他票同構。
- **一行一個旗標,兩個方向都要對得上批次。** 結果檔那一行寫 `"rejudge": true` 才換得掉;批次檔標了改判而結果檔沒寫旗標的,整批不寫入——否則既有那一行會照舊擋下來,改判等於沒做而且看起來成功了。反過來,批次沒標而結果檔自己寫了旗標的同樣整批不寫入,否則「要一張自己的票」就只是慣例。
- **動不了更高的權威。** 改判只碰得到 `llm` / `llm_then_rule`。[[官方明示]]與人工修正(`manual`)碰到即整批不寫入(`judgment_rejudge_refused`),前者是權威資料,後者是使用者看過這一行的證據。

改判是**冪等**的:值已經相同時什麼都不做也不報告,改判票因此與其他票一樣能單獨重跑(Story 39)。

## Consequences

- 判定票數**不隨規則歸納而遞減**;規則的價值全部轉為「驗證既有判定」與「未來新卡的[[差值更新]]」。上面那個「20 張」是本決定作成時的估算,不是承諾:實際張數由每票放得下幾張卡決定,票11 把[[效果句]]重量之後改為兩個系列分開排票,票13 以實測成本定案為 **33 張**(要拆+判 19 × 200 張、只判類型 14 × 300 張)。不變的是「一條也不跳過」。
- 規則層因此必須可稽核:每條規則登記於 `docs/effect_kind_rules.md`,記錄判別條件、覆蓋條數、新增票號,以及變更(過寬、衝突、合併)的理由與票號。
- 判定的成果同樣只由票改動:規範改版後的修正走改判票(上面的票52 修訂),`data/tag_cards.json` 不手改。使用者自己逐卡回報的修正仍然是 `manual`、直接改檔(spec Story 28),那是另一條路,改判票碰不到它。
- 收斂條件是可機器檢查的:全表跑完一輪後規則清單無異動、每條規則覆蓋 ≥ 8 條、衝突清單為空。
