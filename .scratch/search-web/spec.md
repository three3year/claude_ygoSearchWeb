# Spec: 靜態查卡網站(前端搜尋介面)

Status: ready-for-agent

## Problem Statement

專案手上已經有兩份對齊好的資料——[[卡片總表]] `data/cards.json`(14,207 張卡)與[[效果標記表]]
`data/tag_cards.json`(32,637 個[[效果句]],逐句標好十六種[[效果類型]]與[[必發/選發]])——但沒有
任何東西能讓人查它們。`tag_cards.json` 的價值全部鎖在一份 24 MB 的 JSON 裡:要回答
「哪些暗屬性怪獸有誘發即時效果」得自己寫 Python;要回答「哪些卡的效果文提到特殊召喚
**而且那一句是啟動效果**」連 Python 都得寫上幾十行。

一般的查卡網站(salix5/query、ygoprodeck)只能對整段卡文做關鍵字比對,答不出這類問題,
因為**它們沒有效果句層級的結構**。搜「特殊召喚」得到的是「卡文某處出現這四個字」,而使用者
真正想問的是「某一個效果做這件事,而那個效果是誘發即時」。這正是[[效果標記表]]花了 20 多票
判出來的東西,目前零使用者。

三個具體的資料落差擋在前面:

1. [[卡片總表]]存的是 cdb 原始位元(`type: 65538`、`race: 0`、`attribute: 0`),專案裡**沒有任何
   地方**把它翻成「速攻魔法/暗/龍族」。這份對照表要從零建立。
2. 兩份資料合計 33 MB,直接餵給瀏覽器不可行。
3. 站要架在 GitHub Pages 上,只吃靜態檔、不能有後端、不會幫忙跑建置。

## Solution

建立**零建置的純靜態查卡網站** `web/`,由建置期產生的[[前端索引]] `web/data.js` 驅動,
架在 GitHub Pages 上。

四條搜尋軸:**卡名關鍵字**(中/日/英三選一 + [[卡片密碼]] + 別名)、**效果文關鍵字**、
**卡片參數**([[卡片子類型]]/屬性/種族/等級階級/連結值/刻度/攻守/連結標記)、
**[[效果類型]]+[[必發/選發]]**,外加 MD 稀有度、Genesys 點數、OCG・TCG 三個欄位。
軸間 AND、軸內 OR,分類類條件用三態鈕(點一下=包含,再點=排除)。

兩個語意決定是這個站與一般查卡站的分水嶺,兩者都源自效果句層級的結構:

- **句層耦合**:效果文關鍵字與效果類型並用時,**必須命中同一個效果句**。這正是使用者真正
  想問的問題形狀——「找一個會做某件事的誘發即時效果」,而不是「這張卡某處有這四個字、
  另一處有個誘發即時」。命中的那一行會被標亮,標亮才有意義。
- **排除素材行**:效果文關鍵字**不掃 `role = 素材指定` 的 2,358 行**。搜「融合」時,574 張
  融合怪獸的素材寫法會把真正的答案淹掉。[[效果標記表]]逐句判過 `role`,所以這件事做得準,
  而一般查卡站做不到。

前端沿用 oldProject(`F:\AiProject\oldProject`)驗證過的**顯示手法**:卡圖 + 卡面資訊排版、
卡文逐效果句分行、命中行標亮並掛 badge、[[同名異圖卡]]分區、連結標記九宮格、分頁器。
`style.css` 與 `render.js` 從該專案拉過來改;搜尋引擎與條件 UI 因資料形狀與條件模型都不同
而重寫。**本站是全新獨立的站,不是 oldProject 的接班人**——不承諾補齊該站的效果標籤、
時機、檢索路徑三軸([[效果 Tag]] 的 `tags` 欄位目前全空,[[分類表]]未定稿)。

cdb 位元 → 值域的轉換住在**建置期**的[[值域正典]]:值域與中文表隨索引一起輸出成
`window.VOCAB`,HTML 不寫死任何選項、按鈕由 JS 依 VOCAB 生成。這是為了擋掉一種無聲失效——
值域漏一碼,某批卡就從搜尋結果消失,不報錯、不白屏,只是結果少了幾百張而沒有人會察覺。

## User Stories

### 搜尋:卡名與卡文

1. As a 使用者, I want 用中文、日文或英文卡名搜尋並能切換語言, so that 我看到日文卡表或英文
   牌表時不必先translate 就能查。
2. As a 使用者, I want 卡名搜尋同時比對 `※` 別名, so that 用舊譯名或另一種中文譯名也找得到卡。
3. As a 使用者, I want [[卡片密碼]]有自己的搜尋欄位, so that 我從卡面左下角抄一組數字就能
   直接查。(2026-08-14 使用者裁示改寫:原文是「卡名框也接受卡片密碼」,票03 實作時
   改成獨立欄位並排在卡名框上方,卡名框只比對卡名——見票03 Comments。)
4. As a 使用者, I want 卡號搜尋涵蓋[[同名異圖卡]]的異圖密碼, so that 我拿到的是異圖卡面時
   也查得到本尊。
5. As a 使用者, I want 卡名與效果文兩框都支援 `%` 萬用字元, so that 我能查「青眼%龍」這種
   記得頭尾但忘了中間的卡。
6. As a 使用者, I want 效果文關鍵字逐[[效果句]]獨立檢查, so that 「墓地%手牌」只在同一個效果
   裡同時出現才算命中,而不是散落在兩個無關的效果。
7. As a 使用者, I want 效果文關鍵字不掃 `role = 素材指定` 的行, so that 搜「融合」不會被 574 張
   融合怪獸的素材寫法淹沒。
8. As a 使用者, I want 效果文關鍵字仍然掃到召喚條件與使用次數限制那些行, so that 「不能通常
   召喚」「1回合只能使用1次」這類我確實想查的限制文字找得到。
9. As a 使用者, I want 命中的效果句整行標亮、關鍵字本身再上色, so that 我一眼看到是哪一個
   效果讓這張卡被選中。

## Implementation Decisions

### 領域詞彙

本次新增三個詞彙,寫入 `CONTEXT.md`:

- **[[前端索引]]** —— `web/data.js`,由[[卡片總表]]與[[效果標記表]]產出的建置產物。
- **[[值域正典]]** —— cdb 位元 → 值域 + 中文表的單一來源,住在建置期。
- **[[卡片子類型]]** —— 搜尋介面用的怪獸/魔法/陷阱細分值域(cdb 實際出現 23 種)。

第三個必須寫進 `CONTEXT.md` 的理由是它**與既有的[[卡片種類]]是兩套不同的值域**,而兩個詞
長得幾乎一樣。[[卡片種類]]是十值、怪獸不細分,它服務的是[[效果類型]]的判定([[魔陷卡效果]]
的值就是它的名字);[[卡片子類型]]是 23 個 cdb 位元,含融合/同調/超量/連結/調整/反轉這些
怪獸細分,它服務的是搜尋。不寫下這個辨析,下一個人會拿[[卡片種類]]去做子類型按鈕,然後
發現怪獸只有一顆鈕。

兩份 ADR 記錄本次最難反轉的決定:

- **前端零建置檔案協定** —— 無 npm、無 bundler、無框架、無 ES modules。
- **[[值域正典]]住建置期** —— 對應 oldProject ADR-0015,病歷是「漏抄一個碼讓 29 個效果無聲消失」。

### 接縫與模組

沿用專案既有架構模式(`card_list` / `faq_info` / `tag_card` 三個模組都是):
**單一純函式管線 + CLI 薄殼,薄殼不納入自動測試**。新增 `script/web/` 與 `card_list`、
`faq_info`、`tag_card` 並列。

**接縫 1(主)**:`build_index(卡片總表條目, 效果標記表條目) -> (index, report)`

純函式。cdb 位元解碼、效果句組裝、`role` 標記、`alt_ids` 帶入、`※` 別名抽取、
靈擺 `section` 分區、排序鍵、`VOCAB` 生成,全部是內部實作,一律透過這一個函式測試。

Story 59–62 那四道一致性檢查**長在這個 `report` 裡**,不另開接縫。CLI 薄殼因此退化成
「讀檔 → 呼叫 → 寫 `web/data.js` → 印報告 → 依 report 的 problems 決定 exit code」。
這與 `tag_card` 把驗收條件放進 `build_tag_cards` 的 report、`seal_report.py` 只當薄殼
是同一個結構。

**接縫 2**:[[值域正典]]自檢 —— `vocab.problems()` / `vocab.digest()`

理由與 `tag_card` 把 `rules` 自檢獨立出來完全同構:接縫 1 吃的永遠是 repo 裡那一份正典,
而要測的正是「換一份壞的進來會怎樣」——重複碼、缺中文、排序序不完整、位元對應重疊。
接縫 1 測不到這件事。

**接縫 3**:前端查詢引擎 —— `查詢條件 -> (命中卡片密碼清單, 每張卡的命中效果句索引)`

以 `node:vm` 沙箱 + 最小 DOM stub,依 `web/index.html` 的 `<script src>` 順序載入**真實的
前端程式碼**執行。零 npm 依賴,不進 `package.json`,前端檔案不需要為了可測而加任何
`module.exports` 之類的改動。**前例:oldProject 的 `scripts/audit/frontend_parity.js`**,
同樣的沙箱手法、同樣零依賴。

回傳「每張卡的命中效果句索引」而不只是卡片清單,是因為**句層耦合(Story 26)與排除素材行
(Story 7)這兩個語意只能從命中位置驗證**——光看命中了哪些卡,分不出引擎是真的做了同句
交集還是碰巧兩個條件都在同一張卡上成立。

前端模組切分沿用 oldProject 的分層(工具/引擎/呈現/主流程),呈現層採**全量重繪**——本站
有分頁,單次渲染量只有一頁;差異更新需要「知道上次渲染了什麼」,那是把耦合換個名字留下來。

### [[前端索引]]的資料結構

輸出 `web/data.js`,**入版控**(GitHub Pages 直接吃 repo 內容,產物不進版控就沒有站)。

### 卡文的組裝

[[效果句]]的 `text_zh` 是卡文的**連續子字串**。實測 14,207 張卡中 13,016 張的效果句串接後
與卡文完全相等(忽略空白),689 張沒有效果句,502 張有缺口——而缺口**全部是結構標記,
零效果文字損失**:

- 759 處 `【靈擺效果】` / `【怪獸效果】` 段落標頭 → 由 `pz` 欄位在呈現層重建
- 117 處 `※` 別名 → 建置時抽出存進 `ax`
- 5 處標頭碎片(`】這個卡名的靈擺效果`)→ 同第一種

因此 Story 62 的覆蓋檢查以「容許這兩種已知缺口」為門檻,出現第三種即建置失敗——那代表
拆句或卡文出了預期外的變化。

### [[值域正典]]

單一來源,產出兩樣東西:cdb 位元/整數 → 短碼的解碼表,與短碼 → 中文 + 宣告序的對照表。
宣告序同時是**按鈕排列順序**與**領域序排序的比較序**(Story 37),兩者共用同一份宣告——
oldProject 的 `RACES = VOCAB.race.map(e => e.zh)` 就是這個做法,註解寫著「與宣告序同一份」。

值域規模(2026-08-13 實測):

- 大類 3(怪獸 9,280 / 魔法 2,858 / 陷阱 2,069)
- [[卡片子類型]] 23 種,cdb 實際出現者全收:效果 8,473、永續 1,076、通常 722、調整 602、
  超量 598、融合 574、速攻 570、同調 536、連結 468、靈擺 390、特殊召喚 346、場地 336、
  裝備 282、儀式 232、反轉 212、反擊 178、二重 45、靈魂 42、同盟 40、卡通 18。
  **[[衍生物]]位元 0 張**——[[卡片總表]]本來就不收錄,正典仍登記這個碼,值為 0 時報告要看得到
- 屬性 7(cdb 值 1/2/4/8/16/32/64),另有 `0` = 無屬性
- 種族 26(cdb 位元 1 ~ 0x2000000),另有 `0` = 無種族
- [[效果類型]] 16、[[必發/選發]] 2、`role` 3、連結標記 8
- MD 稀有度 4 + 未實裝、`ot` 3

**怪獸參數的清理不歸本模組管,歸[[卡片總表]]。** cdb 為 79 張魔陷卡(罠モンスター:伯吉斯
異獸、詛咒的雕像、鏡像的沼澤人…)存了完整的 `race` / `attribute` / `level` / `atk` / `def`,
但那不是卡片的參數,是它**變成怪獸之後**的參數,寫在效果文的括號裡而不是印在卡面上。
`cards.json` 早就對連結怪獸的 `def`、非靈擺卡的 `scale` 做同樣的閘門,魔陷卡這一類只是
漏了——修在來源層,見 `.scratch/card-list/issues/07-non-monster-cards-have-no-monster-params.md`。

**本模組的職責因此只剩一道不變式斷言**:索引裡「大類是怪獸 ⟺ 有種族與屬性」必須雙向
成立,不成立即建置失敗。這是防禦縱深,不是過濾——真正的清理在上游。card-list 票 07
完成前,`build_index` 保留過渡用的大類閘門。

### 搜尋語意

- **軸間 AND、軸內 OR**。分類類條件為三態:未選 / 包含 / 排除。排除優先於包含
  (同一軸同時被包含與排除時以排除為準)。
- **句層條件的交集**:效果文關鍵字與[[效果類型]]/[[必發/選發]]並用時取**效果句層級的交集**,
  一張卡只要存在一個效果句同時滿足全部句層條件即命中,該效果句進命中集合。
- **效果文關鍵字排除 `role = 素材指定`**(2,358 行),固定規則、不提供開關。副作用已知悉:
  在效果文框搜「青眼白龍」不會撈到把它寫在素材行的融合怪獸,但卡名框搜得到本尊。
- **卡名關鍵字**:依所選語言比對對應卡名,中文與日文模式**同時比對 `※` 別名**(沿用
  oldProject `engine.js:249-251` 的行為)。**只比對卡名**——[[卡片密碼]]是另一個欄位。
- **[[卡片密碼]]**:自己一個欄位(排在卡名框上方),比對密碼與 `alt_ids`,數值完全相等
  才算(補零的 `00002511` 也命中)。非數字的輸入不命中任何卡,而不是被當成沒設條件。
- **`%` 萬用字元**:兩個關鍵字框都支援,語意同 SQL LIKE。
- **攻守 `?`**:`?` 與 0 是不同的東西,範圍條件不得把 `?` 當 0 納入;另有獨立條件可單獨
  找出 `?`。連結怪獸沒有守備欄,不算 `?`。
- **[[必發/選發]]的可用性**:已選(包含)的[[效果類型]]全都不承載該屬性時收起該組條件
  (Story 25);**一顆效果類型都沒選時仍然顯示**——那時「必發」自己就是一個有結果的
  條件,Story 24 的「找必須發動的效果」不必先點滿承載的十二顆鈕才問得出來
  (2026-08-14 票06 實作時的判讀,見票06 Comments)。承載關係由[[值域正典]]宣告。
- **空條件**:不設任何條件時列出全部 14,207 張,不擋。

### 排序

預設是**領域序**,沿用 oldProject `cmpCards` 的七層比較:大類 → 靈擺卡排後 → [[卡片子類型]]序
→ 等級/階級/連結值**高到低** → 屬性序 → 種族序 → [[卡片密碼]]升序。第 1、3、5、6 層的序
直接取自[[值域正典]]的宣告序(大類那一層也是,沒有理由只有它手抄)。

第 3 層比的是**卡框**:一張卡帶多個子類型碼(融合效果怪獸是「效果＋融合」),取值域**第一個
分組**(怪獸側的「卡框」;魔法/陷阱側沒有分組,全體都是卡框)中**宣告序最後**的那一個碼。
只看第一個分組是為了擋掉協調同步怪獸——協調屬於「能力」組,拿它來排的話那張卡會從同步
那一團裡被抽出來。靈擺碼在這一層排除,因為第 2 層已經處理過它(否則靈擺融合與靈擺通常
會併成一團)。

另提供排序選單:攻擊力、守備力、等級階級、卡名、[[卡片密碼]],各可升降序。三條語意:

- **空值一律殿後**,升序降序都是。攻守的空值有兩種來源(非怪獸沒有那個欄位、`?` 是負的
  哨兵值),兩種都不是數值。`?` 當 0 排會讓 83 張攻擊力未知的怪獸混進攻 0 那一團;
  讓空值跟著方向翻則會讓「攻擊力升序」的第一頁變成 5,010 張沒有攻擊力的卡。
- **等級這個鍵只認 `lv`**,連結怪獸在它上面是空值——LINK-3 是連結值、是另一個參數。
  領域序的第 4 層仍然吃 `lk`,那一層問的是規模而不是等級。
- **升降序對稱**:方向連決勝的[[卡片密碼]]一起翻,有值與空值兩批各自反轉、前後關係不變。
  決勝落在唯一鍵上,比較函式因此是全序——結果不靠 `Array#sort` 是不是穩定排序。

卡名比的是**碼點序**而不是 `localeCompare`:後者隨環境的 ICU 版本與 locale 而變,
同一份資料在兩台裝置上會排出不同的順序,而分享出去的網址講的正是「同一個查詢在你那邊
也長這樣」。

排序住在**呈現層**而不是查詢條件裡:換排序鍵不改變命中哪些卡,所以它與分頁同一類,
「排序切換不重跑搜尋」因此是結構上成立的。換鍵時分頁位置歸 1。選單的選項與**切換到該鍵
時的預設方向**由 `Sort.KEYS` 一處宣告,HTML 只留一個空的 `<select>`;領域序沒有方向。

### 網址狀態

按下搜尋時把條件序列化進 `#hash`,`pushState` 語意(留瀏覽器歷史)。載入時解析 `#hash`
還原條件並自動執行搜尋。**自己寫入 hash 觸發的 `hashchange` 必須被擋掉**,否則同一次搜尋
會跑兩遍。三態排除需要能雙向編碼。打字過程不寫 hash,只在按搜尋時寫一次。

## Testing Decisions

好的測試只驗證接縫的**外部行為**:餵合成資料進去、斷言出來的值。不測內部函式、不測中間
產物、不斷言 DOM 結構或 CSS class 名稱(那是實作細節,重構就會壞而且壞得沒有意義)。

先例:`script/card_list/test_cardlist.py`、`script/faq_info/test_faqinfo.py`、
`script/tag_card/test_tagcard.py` —— unittest、fixture 於測試內程式化建立、不碰網路
不碰真實資料檔。前端測試的先例是 oldProject 的 `scripts/audit/frontend_parity.js`
(`node:vm` 沙箱、零 npm)。

### 接縫 1:`build_index`

- cdb 位元解碼:各大類、多位元並存(靈擺通常怪獸同時帶 Normal 與 Pendulum)、
  連結怪獸的 `def` 為 null 不得誤解成 0
- **不變式「大類是怪獸 ⟺ 有種族與屬性」雙向成立**,任一方向不成立即建置失敗
  (餵一張帶種族的陷阱卡進去必須擋下來——這是 card-list 票 07 若退化時的防線)
- 攻守 `?` 與 0 在索引裡可區分
- 效果句組裝:`tx` / `k` / `o` / `ro` 四個陣列同索引對齊
- `pz` 正確標出 `section = pendulum` 的效果句索引
- `※` 別名從卡文抽出進 `ax`,且**不留在** `tx` 裡
- `alt_ids` 帶入 `al`,無異圖的卡不產生該欄位
- 沒有效果句的卡產生 `d`(故事文)而非空 `tx`
- 空值省略而非寫 null
- **report 的四道一致性檢查各自能失敗**(這是重點,不是「跑得過」而是「該擋的擋得住」):
  - 卡片總表有卡而索引沒有 → 失敗

# 增修:側欄軸摺疊與大類兩態化

Status: ready-for-agent
對應票:issues/11-sidebar-axis-collapse-and-cat-two-state.md(2026-08-17 訪談定案)

## Problem Statement

側欄垂直太長。17 個[[軸]]、兩百多顆按鈕全部展開,加上三個文字輸入欄,找一個條件要捲
很久——條件變多之後「搜尋鈕釘在側欄頂端」(票05 Comments)只是止痛,沒有治本。

另一個困惑來源是[[大類]]的排除態:大類只有怪獸/魔法/陷阱三值,排除某一類等同勾選
其餘兩類,排除態是冗餘的;而且點過頭誤入排除態時,對應子類組會整組收起(排除不算
連動展開的條件),使用者看到的就是「子類別突然不見了」——這正是本次「行為不對」回報
的實際成因。

## Solution

**參數軸全部改成可摺疊區塊、預設收起**:側欄初見只剩三個文字輸入欄、搜尋/清除鈕與
一排軸標題列。[[摺疊]]是瀏覽狀態——收起保留條件生效,標題列以已選數提示;與既有的
[[連動隱藏]](取消大類即清空子類組)是兩個機制,語意相反,兩者並存。

**[[大類]]改兩態**(選取/未選),移除排除態;其他軸維持三態。兩件事互相成全:兩態化
消滅了「誤入排除態」這個困惑源,摺疊化把「選了大類才展開子類組」的既有連動升級成
「出現且自動展開」。

## Implementation Decisions

### 領域詞彙

本次新增三個詞彙,已寫入 `CONTEXT.md`:

- **[[大類]]** —— 怪獸/魔法/陷阱三分。一直被各處引用卻沒有自己的小節,這次補上,
  並與[[卡片種類]]、[[卡片子類型]]明確劃界。
- **[[軸]]** —— 搜尋介面一組同質條件的單位;軸內 OR、軸間 AND。
- **[[摺疊]] vs [[連動隱藏]]** —— 摺疊是瀏覽狀態,收起**保留**條件生效;連動隱藏是
  條件語意,隱藏即**清空**。兩詞各自 `_Avoid_` 對方,擋掉「收起怎麼有時清有時不清」
  的混淆。

### 摺疊機制

- 每個參數軸加摺疊標題列(軸名 + 已選數),預設**全部收起**;文字輸入三欄與搜尋/清除鈕
  常駐不摺疊。
- 各軸獨立展開/收起,**可同時多開**,非手風琴式。
- 收起**不清空**條件(與連動隱藏相反);已選數讓收起的條件保持可見。
- 摺疊狀態**不記憶**:不進網址 hash、不進 localStorage。
- 自動展開的三個時機:大類選取 → 對應子類組;效果類型的承載出現 → [[必發/選發]]軸;
  網址還原 → 所有帶已選條件的軸(含連動出現者)。
- 「清除」重置條件並將全軸收回預設收起。
- 窄螢幕(≤720px)外層側欄的摺疊行為不變,內外兩層摺疊各自獨立。

### 大類兩態化

- [[大類]]的狀態循環從 未選→包含→排除 改為 未選⇄選取;讀出條件時不再產生排除值。
- 態數(兩態/三態)成為**軸宣告的一部分**,由軸清單(`Query.axes()` 的形狀)攜帶,
  點擊處理照宣告循環——不是在事件處理裡對大類寫特例。
- 其他軸(含子類型)維持三態,排除優先語意不變。
- 大類按鈕 tooltip 文案同步改為兩態說明。
- **舊網址不需相容處理**:本版尚未公開,不存在帶大類排除的既有分享連結。

### 純規則(沿用接縫 3 模式)

三個規則抽成 Query 的純函式,DOM 層只照答案動作——與既有的 `optionalAvailable`
(必發/選發出不出得來)、`critCount`(窄螢幕摺疊鈕的條件數)完全同一個結構:

1. **軸的態數宣告**:軸清單標記大類為兩態。
2. **還原展開判定**:`查詢條件 → 該展開的軸集合`。
3. **逐軸已選數**:`查詢條件 → 各軸的已選條件數`(critCount 的逐軸版)。
