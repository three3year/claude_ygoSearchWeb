# Spec: 效果標記表定版收尾

Status: ready-for-agent

本文件是 `spec.md`(建置期)的續篇,範圍是**把已經建好的[[效果標記表]]收到可交付狀態**。票號延續同一條專案級序列(`docs/effect_kind_rules.md` 的「新增票號」欄),因此票仍放在 `.scratch/tag-card/issues/`。

## Problem Statement

[[效果標記表]]已經建成:14,207 張卡、32,593 條[[效果句]],其中 17,381 條由[[官方明示]]決定、8,594 條由判定票逐條判出,耗掉 50 張票。它距離「網站可以直接吃」只差 0.15%——但就停在那裡。

具體卡在五個地方:

1. **18 條 `kind: null`**。其中 17 條是同一個原因(17 張卡沒有官方日文文本),1 條是官方用了一種管線認不得的標頭寫法。票09 的第一條驗收就是「全表無殘留 `kind: null`」,過不了。
2. **3 筆 `rule_llm_conflict`**。票09 的收斂條件要求這份清單為空。
3. **兩張 `needs-triage` 的票沒人裁決**(票12、票17),一張 `ready-for-agent` 的票**前提是錯的**(票55 假設「等日文資料補齊」,但那批卡的日文永遠不會出現)。
4. **[[規則層]]的獨立驗證只看一致率、不看分母**。票11 曾讓 R2 的驗證分母從 71 條掉到 1 條,而它照樣印 `PASS`。這個洞在封版之後才真正危險——那時不會再有人像 33 張判定票那樣逐條看過全表。
5. **33 張判定票替 `docs/effect_kind_guide.md` 補進的規則,從來沒有回頭驗證過**。規範是逐票長出來的,後加的判準是否打壞了前面判對的行,目前無人知道。

同時,網站第一階段確定要提供[[效果類型]]篩選——那是這個站相對於現有查卡站的唯一差異化功能。查詢層要敢直接讀這份檔案,靠的正是票09 的定版報告:格式、完整性、收斂三者都被驗過一次。

## Solution

七個動作的**有序**收尾集合,終點是票09 定版。順序不是偏好而是約束:任何改到[[規則層]]定義或管線的動作,都會讓規則定義指紋變動,而票09 的收斂條件第一項是「規則清單本輪無異動」——所以票09 必須是最後一個動作,且它之前要有一次乾淨建置讓指紋穩定。

| 序 | 票 | 動作 |
|---|---|---|
| 1 | 票12 | [[規則層]]的獨立驗證加**官方明示分母下限**,不足時判讀印「不足」而非 `PASS`,並列進票09 的收斂條件第四項 |
| 2 | 票17 | [[官方明示]]的行內 `『●』` 歸屬補上序數與全稱解析,撿回 3 條被丟掉的官方類型 |
| 3 | 票61 | 收緊 R17:效果句本身是 `●` 子效果、發動寫在領起句上時不寫[[影子預測]] |
| 4 | 票60 | 標頭解析認得 `【〈編號〉の『●…』の効果について】`,補判該卡 |
| 5 | 票55 | 17 張無官方日文文本的卡改走**繁中單側拆句 + 繁中判定**(ADR-0006) |
| 6 | 票62 | [[遮蔽測試]]**重判輪**:改版後的規範套回第二期五輪的舊樣本,確認沒有回歸 |
| 7 | 票09 | 最終合併驗收定版 |

做完之後,`kind: null` 歸零、衝突清單歸零、五張未結票全部關閉,`data/tag_cards.json` 帶著一份定版報告成為網站階段的輸入。

## User Stories

1. As a 網站查詢層, I want [[效果標記表]]全表沒有殘留的 `kind: null`, so that 「找出所有有誘發即時效果的卡」不會因為部分卡片沒有值而給出不完整的結果。
2. As a 網站查詢層, I want 一份定版報告載明總卡數、總效果句數、各 `source` 佔比與各[[效果類型]]分布, so that 我可以在建索引之前確認這份檔案的形狀符合預期。
3. As a 網站查詢層, I want 每個[[效果句]]的 `text_zh` / `text_ja` 都被驗證過是對應卡文的連續子字串, so that 我可以安全地用偏移量把效果句對回卡文顯示。
4. As a 網站查詢層, I want `optional` 只出現在誘發即時與誘發兩類、`role` 只出現在效果外文本, so that 前端的篩選介面不必處理沒有意義的欄位組合。
5. As a 使用者, I want 那 17 張沒有官方日文文本的 TCG 限定卡也有[[效果類型]], so that 我用類型篩選時它們不會憑空消失。
6. As a 使用者, I want 那 17 張卡被標成 `confidence: low` 並在定版報告裡單獨列出, so that 我知道全表哪一批的可信度最低、該優先抽查。
7. As a 使用者, I want 那 17 張卡的判定基礎是繁中卡文而不是社群回譯的日文, so that 判定依據是我看得懂、也驗得了的那份文本。
8. As a 使用者, I want 官方用「`『●』の効果はいずれも…』」「`Ｎつ目の『●』`」寫出範圍時它的類型會被採用, so that 官方已經講清楚的裁定不會因為管線讀不懂而被丟掉。
9. As a 使用者, I want 官方用 `【①の『●３つ』の効果について】` 逐項給不同類型時效果句會被拆開, so that 兩種類型不會因為擠在同一個 `kind` 欄位而讓其中一種從查詢層消失。
10. As a 使用者, I want 同一次發動的多個 `●` 選項不會被標成不同的[[效果類型]], so that 我不會在一張卡上看到「它有永續效果」這種與規則事實不符的敘述。
11. As a 判定者, I want [[規則層]]的每一條規則都標明它的驗證分母, so that 我不會把「1/1 一致」誤讀成「這條規則被驗證過」。
12. As a 判定者, I want 驗證分母不足的規則被印成「不足」而不是 `PASS`, so that 資料層的正當演進抽掉某條規則的驗證基礎時,它會出聲而不是靜靜地繼續上工。
13. As a 判定者, I want [[遮蔽測試]]的重判輪把改版後的規範套回舊樣本, so that 我知道 33 張判定票補進來的新判準有沒有打壞原本判對的行。
14. As a 判定者, I want 重判輪不計入首判輪的輪數上限, so that 回歸檢查不會消耗代表泛化能力的那個額度。
15. As a 判定者, I want 那 17 張卡的[[拆句表]]紀錄只驗繁中側的無遺漏覆蓋, so that 缺日文的事實不會讓一筆結構正確的拆句紀錄失效。
16. As a 判定者, I want 那 17 張卡的 `text_hash` 改以繁中卡文計算, so that 繁中卡文變動時整筆仍會失效並退回未拆狀態。
17. As a 判定者, I want 既有的 4 筆退化拆句紀錄被清掉重來, so that 它們不會再以「整團一段」的形式落進每一次的判定批次。
18. As a 維護者, I want 這 17 張卡日後若逆輸入 OCG 能自動回到正規流程, so that 我不需要為它們維護一條永久的特例路徑。
19. As a 維護者, I want 收尾動作有明確的執行順序與理由, so that 我不會因為在票09 之前改了規則而讓收斂條件驗不過、白跑一輪。
20. As a 維護者, I want `rule_llm_conflict` 清單歸零是靠收緊規則而不是靠[[改判]], so that 判定者原本一致的標法被保留,而不是為了讓清單好看去改動正確的資料。
21. As a 維護者, I want [[拆句表]]的三道驗證在全表的失敗筆數為 0, so that 我可以確定沒有任何一筆拆句紀錄是結構壞掉卻仍在生效的。
22. As a 維護者, I want 舊式整團裡沒有拆句表紀錄的那些被逐筆列出理由, so that 「判定者明講拆不出來」與「還沒輪到」這兩種狀態不會混在一起。
23. As a 維護者, I want `data/tag_cards.json` 的格式(一卡一物件、依[[卡片密碼]]升冪、`indent=2`、保留結尾換行)被檢查, so that 它的 git diff 在往後的[[差值更新]]裡仍然讀得懂。
24. As a 維護者, I want `README.md` 的目錄與後續階段說明加入效果標記表與其腳本目錄, so that 下一個接手的人知道這份資料是什麼、怎麼重建。
25. As a 維護者, I want `spec.md` 裡「[[效果類型]]值域固定為六種」的舊敘述被更正為十六種, so that 規格文件不會與 ADR-0004 / ADR-0005 和 CONTEXT.md 相矛盾。
26. As a 維護者, I want CONTEXT.md 的[[拆句表]]詞條容納繁中單側形態並指向 ADR-0006, so that 領域詞彙表描述的是實際存在的資料形態。
27. As a 維護者, I want 收尾期間不新增測試縫隙, so that 這批改動的驗證方式與既有 3,459 行測試一致,不引入第二套做法。

## Implementation Decisions

### 執行順序是硬約束

票09 必須排最後,且它之前要有一次**乾淨建置**讓規則定義指紋穩定。票12、票17、票61、票60、票55 之中任何一個改到規則定義或管線,都會讓當次建置的「規則清單本輪有異動」為真,收斂條件第一項即不成立。票62 的重判輪需要**定版前的最終規範**,所以排在所有規範改動之後、票09 之前。

### 票12 —— 驗證分母下限

[[規則層]]現有兩道門檻不對稱:覆蓋條數有下限(不足即不進規則層),一致率沒有分母下限。新增一個與覆蓋下限平行的**官方明示分母下限**常數;分母不足的規則,獨立驗證表的判讀欄印「不足」而非 `PASS`,並成為票09 收斂條件的第四項。門檻值取與覆蓋下限相同的量級即可——現況全表最小分母是 10,設下限不會攔到任何現有規則,它買的是封版之後的預警能力。分母不足**不停用規則**,理由與一致率未達門檻時相同:停用會把問題藏起來。

### 票17 —— 行內 `『●』` 的歸屬

標頭形態的序數解析已經存在(`【Ｎつ目の●について】`),行內引用沒有用上同一套。三種寫法要處理:全稱(`いずれも`、`２つ以上の`)→ 該編號效果**全部**的 `●` 套同一個類型;序數(`Ｎつ目の『●』`)→ 沿用既有的序數對位;其餘純 `『●』` 維持歸入引號歧義報告——官方沒說就是沒說,不猜。實測基準:全稱 1 條、序數 2 條、不可解 4 條。

### 票61 —— 收緊 R17

R17(直接攻撃 → 永續效果)在三張卡上對「列舉型領起句底下的某一個 `●` 選項」開火,而同一組選項裡的其他 `●` 顯然不是永續效果。判別條件新增排除:效果句本身是 `●` 子效果、且其領起句含發動子句時不寫[[影子預測]]。這是**規則過寬**而非判定錯誤——判定者把同一次發動的三個選項標成同一個類型是正確且一致的做法,走[[改判]]會製造出「同一張卡同時有誘發效果與永續效果」這種與規則事實不符的結果。變更依 `too_broad` 記入規則變更記錄。

### 票60 —— 標頭的編號前綴

標頭正則多認一種前置修飾(`〈編號〉の`);先量全表範圍(所有含 `●` 卻解析不出規格的 `【…】` 標頭),不只收編號前綴這一種形態。放寬前必須確認不會拆到已經判過的段。回傳的 label / ordinal 對位邏輯不變。

### 票55 —— 繁中單側拆句與繁中判定(ADR-0006)

原票的前提「補齊來源資料的日文卡文與補足情報」**不可能達成**:那 17 張全部是 TCG 限定卡,從未在 OCG 發行,官方日文資料庫沒有它們的頁面。管線的日文原文取自[[官方 Q&A 快取]]而非 `ja-JP.cdb`,因此它們在判定鏈上整團落空。

決定(見 ADR-0006):

- [[拆句表]]容納**繁中單側**形態——段落只記繁中原文,日文側留空,兩側語序對照不適用。無遺漏覆蓋只驗繁中側;引用交叉驗證因為沒有[[補足情報]]而自動略過。
- `text_hash` 對這批改以繁中卡文計算。這使該欄位的語意從「日文原文的雜湊」推廣為「判定基礎文本的雜湊」。
- 判定從繁中卡文做,結果一律 `source: llm`、`confidence: low`、[[影子預測]]為空。這是 ADR-0002 的明文例外:[[規則層]]全部掃日文原文,掃不到這批。
- 既有 4 筆退化拆句紀錄清掉重來。
- 票09 的定版報告單獨列出這 17 張。

選繁中而非英文原文,理由記在 ADR-0006:英文在權威性上更正確(對這批卡英文就是官方原文),但判定規範整份繞著日文硬性寫作慣例長成,英文沒有對應判準可套,而且 TCG 卡的英文類型標記會一路保留到繁中譯文。

### 票62 —— 重判輪而非首判輪

[[遮蔽測試]]分首判輪(新樣本,代表泛化能力,計入輪數上限)與重判輪(舊樣本,確認沒有回歸,不計上限)。本次跑**重判輪**:把第二期五輪的既有樣本重新判一次,對照當時的分數。理由是首判輪已經連續五輪指向同一個結論——剩下的錯判是尾部的新形態而非規範寫錯,再抽新樣本的期望值不變;而「後加的判準有沒有打壞前面判對的行」這個問題從未被回答過,且正是封版最該擔心的事。

分數若下降,修正對象是規範文件而不是重刷分數;標準答案事後消失的那些行照既有規則處理(整個 key 不見 → 樣本過期、判不通過;官方類型被撤回 → 排除於分母)。

### 票09 —— 驗收條件的增補

在原有驗收項之外增加:收斂條件第四項(每條規則的驗證分母 ≥ 下限);那 17 張繁中判定卡的專節(無官方日文文本、無官方明示、無影子預測);並註明本票必須排在所有規則與管線改動之後。原有的「全表無殘留 `kind: null`」**維持不放寬**——選了繁中判定路線之後,18 條 null 會真的歸零。

### 文件債

`spec.md` 的 User Story 4 寫「[[效果類型]]值域固定為六種且不會擴充」,ADR-0004 / ADR-0005 之後應為十六種(CONTEXT.md 已正確)。CONTEXT.md 的[[拆句表]]詞條要容納繁中單側形態並指向 ADR-0006。

## Testing Decisions

**好的測試只驗外部行為。** 這批改動的外部行為全部是「同樣的輸入,建置流程吐出的[[效果標記表]]條目與報告有什麼不同」——不是某個正則匹配到什麼、某個內部函式回傳什麼。

**縫隙:沿用既有的兩道,不新增。**

- **建置管線的頂層純函式**(卡片總表 + 補足情報 + 拆句表 + 判定結果 → 條目 + 報告)。票12、票17、票55、票60、票61 的行為**全部**可以在這一個回傳值上觀察:官方明示的歸屬結果、影子預測與衝突清單、拆句驗證的失敗筆數、規則驗證表的分母與判讀、效果句的值與 `confidence`。這是這個模組最高的縫隙,而且已經是既有 3,459 行測試在用的那一道——先前每一張改管線的票(票10、票11、票14、票15、票16、票51、票58)都在這裡加測試,直接照抄那個做法。
- **遮蔽測試的計分純函式**(標記表 + 樣本 + 作答 → 分數與分桶)。票62 用它,既有 519 行測試在用同一道縫隙。

**逐票的測試重點:**

- 票12:分母不足的規則在報告裡的判讀不是 `PASS`;分母充足時行為不變;收斂條件會因為分母不足而不成立。
- 票17:全稱寫法讓該編號下所有 `●` 取得同一類型;序數寫法對到指定的那一個;不可解的純 `『●』` 仍進引號歧義報告(不因放寬而被誤套)。
- 票61:三個實測個案不再產生影子預測;R17 原本正確的覆蓋不受影響(覆蓋條數與官方明示驗證分母的變動要在測試裡釘住);衝突清單為空。
- 票60:帶編號前綴的標頭會拆;標頭底下沒有類型詞時**仍然拆**(拆句依據是標頭本身,類型另算);引用橫跨拆點時仍不拆。
- 票55:繁中單側拆句紀錄通過驗證並產生多個效果句;無遺漏覆蓋只驗繁中側;`text_hash` 由繁中計算且繁中變動會使其失效;這批行不產生影子預測;`confidence` 為低。
- 票62:計分行為本身不改,重判輪是**執行**而非程式變更;若過程中發現計分缺陷才補測試。

## Out of Scope

- **[[效果 Tag]]與[[分類表]]** —— `tags` 欄位維持全空。產生方式(embedding 分群 / 規則優先 / 逐票全量判)留到該階段開工前再定。
- **查卡網站的 spec 與實作** —— 封版之後另立。已定的只有兩件:第一階段包含[[效果類型]]篩選;形態是純靜態前端,查詢索引是由[[卡片總表]]與[[效果標記表]]算出的**建置產物**(約 1.6MB gzip),不是來源檔。
