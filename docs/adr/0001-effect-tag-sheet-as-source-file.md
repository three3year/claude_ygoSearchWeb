# 效果標記表是入版控的來源檔,不是建置產物

[[效果標記表]]的判定結果會被使用者逐卡回報誤標並手工修正,而這些修正必須活過每一次重跑。前一世代把它當建置產物、修正靠外掛的 `effect_kind_overrides.json`,結果是修正與資料分離、override 檔隨規則演進而失效、且無法從資料本身看出某一行是誰判的。因此本專案改為:效果標記表是入版控的**來源檔**,一卡一物件、一欄位一行(`indent=2`)、依卡片密碼穩定排序,每個效果句帶 `source` 欄位(`official` / `rule` / `llm` / `llm_then_rule` / `manual`)。

判別「哪些行重跑時會被重算」的界線是**這一行裡有沒有一次性的成果**:`manual`(使用者的修正)、`official`(權威來源的答案)、`llm` / `llm_then_rule`(判定票的產出)都是判定一次就算數,永不被覆蓋;`rule` 是當前規則層對當前文本的純函式輸出,沒有成果可保留,因此照常重算——否則規則層一旦改動就再也推不到資料上。

## Consequences

- override 檔那一層不再需要——它原本只是為了對抗「產物會被覆寫」而存在。
- 重跑不再是冪等的純函式輸出,而是「既有檔 + 新來源 → 新檔」的合併,因此建置管線必須吃既有標記表作為輸入(見 `build_tag_cards` 的 `existing` 參數),CLI 薄殼預設把輸出檔讀回來當這個參數。
- 效果句需要一個穩定鍵才能讓修正對得回去:`(卡片密碼, section, index)` 搭配 `text_hash`;雜湊變動時不覆蓋而是把該行的 `needs_review` 標成 `true`。這個旗標寫在資料裡而不只在報告裡,因為它必須跨重跑存活到使用者真的看過為止——使用者把它改回 `false` 就是結案。
- 拆句法變動可能讓某一行整個消失,帶著它的判定一起蒸發。合併時對不到任何一行的既有判定列進報告的「既有判定對不到任何一行」,不靜靜丟掉。
