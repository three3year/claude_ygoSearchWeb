# Spec: 卡片總表(Card List)建置管線

Status: ready-for-agent

## Problem Statement

我想取得遊戲王 OCG 的完整卡片總表作為後續自建查卡網站的資料基礎。現有的 salix5 查詢網站只能一頁 50 張地瀏覽,無法一次取得全部卡片資料;而且我需要的是一份自己持有、可長期維護的資料,不能即時依賴外部網站。

## Solution

不爬網頁,直接使用公開的 SQLite 卡片資料庫作為來源,建置一份整合的**卡片總表**(JSON 格式):

- 繁中卡名與卡文來自 salix5/cdb 的 `cards.cdb`
- 日文/英文卡名來自 mycard/ygopro-database 的 `locales/ja-JP`、`locales/en-US`,以**卡片密碼**對齊
- 只收錄有正式 8 位數卡片密碼的已發售卡(排除先行卡)
- 之後以手動觸發的**差值更新**維護,只維護整合後的這一份總表

## User Stories

1. 身為專案擁有者,我想執行一個建置指令就從來源 cdb 產出完整的 `cards.json`,這樣我就能拿到一份自持的卡片總表。
2. 身為專案擁有者,我想讓總表只收錄有正式 8 位數卡片密碼的卡,這樣先行卡(暫時 9 位數編號)就不會混入總表。
3. 身為專案擁有者,我想讓每張卡帶有繁中卡名與繁中卡文,這樣總表就能支撐之後的中文查卡。
4. 身為專案擁有者,我想讓每張卡盡可能帶有日文卡名與英文卡名,這樣之後我用日文或英文卡名也能搜到卡。
5. 身為專案擁有者,我想在日/英卡名來源缺漏某張卡時該欄位留空而非整張卡失敗,這樣單一來源的缺漏不會影響總表完整性。
6. 身為專案擁有者,我想讓每張卡帶有卡種、屬性、種族、等級/階級/Link值、攻擊力、守備力、靈擺刻度、Link箭頭、系列(setcode)等數值欄位,這樣之後的進階篩選才有欄位可用。
7. 身為專案擁有者,我想知道建置完成後總共收錄了幾張卡、排除了幾張、日英卡名覆蓋率各是多少,這樣我能判斷來源資料的品質。
8. 身為專案擁有者,我想再次執行更新指令時以差值更新處理——只比對出新增與變動的卡併入總表,這樣更新快速且變動範圍可審閱。
9. 身為專案擁有者,我想在差值更新後看到這次新增了哪些卡、修改了哪些卡的報告,這樣我能確認更新內容符合預期。
10. 身為專案擁有者,我想讓總表輸出為結構清楚的 JSON 且鍵值順序穩定,這樣 git diff 能清楚呈現每次更新的實際變動。
11. 身為專案擁有者,我想讓下載來源檔的步驟與整合邏輯分離,這樣網路不通時我仍能用已下載的來源檔重跑整合。
12. 身為專案擁有者,我想用迷你 fixture 資料庫執行自動化測試,這樣不用連網、不用下載完整資料庫就能驗證管線正確性。
13. 身為未來的網站開發者(我自己),我想讓總表的欄位命名與結構在這階段就定稿,這樣下一階段的效果 Tag 管線與網站可以直接消費這份資料。
14. 身為未來的效果 Tag 管線,我需要總表保留完整未加工的繁中卡文原文,這樣拆效果句時才有正確的輸入。
15. 身為專案擁有者,我想讓 Token/衍生物被排除在總表之外,這樣查卡結果不會混入不能組牌的臨時物件。
16. 身為專案擁有者,我想讓同名異圖卡合併為主卡一筆並保留異圖密碼於副欄位,這樣同一張卡不會在查詢結果出現多筆。

## Implementation Decisions

- **語言與依賴**:Python,只用標準庫(`sqlite3`、`json`、`urllib`),零安裝依賴。
- **管線架構(單一接縫)**:核心是一個純函式——輸入「來源 cdb 檔路徑集合(+可選的既有總表)」,輸出「總表資料結構」。下載、檔案讀寫在此接縫之外的薄殼處理。全量建置與差值更新走同一條管線:差值更新 = 既有總表 + 新來源 → 合併後總表 + 變動報告。
- **來源**:
  - 繁中:salix5/cdb Releases 的 `cards.cdb`(`datas` + `texts` 兩表)。不使用 `pre-release.cdb`。
  - 日英:mycard/ygopro-database `locales/ja-JP/cards.cdb` 與 `locales/en-US/cards.cdb`,以卡片密碼(id)對齊。實作時先驗證覆蓋率;若明顯不足,再評估補充來源(記錄於報告即可,本階段不自動混源)。
  - MD 稀有度:masterduelmeta.com API(`konamiID` 即卡片密碼,分頁抓取、需 User-Agent),彙整為本地 JSON 後以密碼對齊;主卡沒對到時嘗試異圖密碼。未實裝 MD 的卡留空字串(空值本身代表「MD 未實裝」)。(票 05 追加)
  - Genesys 點數:YGOPRODeck API 全量 dump(`misc_info.genesys_points`,以密碼對齊;**必須帶 `format=genesys` 參數欄位才會出現**),萃取為本地 JSON;主卡沒對到時嘗試異圖密碼,未列點為 0。(票 06 追加)
- **收錄規則**:以 `cards.cdb` 為卡片全集,過濾條件為 id 是正式 8 位數卡片密碼(id < 100000000)。同時排除 Token/衍生物(`type` 含 TYPE_TOKEN 位元 `0x4000`;注意不要誤用 `0x4000000`,那是 Link 怪獸位元)——衍生物不是可組牌實卡,實測 cards.cdb 內有 265 筆。
- **同名異圖卡合併**:`alias` 不為 0 且卡名與主卡相同的條目視為異圖卡,合併進主卡——主卡一筆為代表,異圖密碼收進 `alt_ids` 副欄位。alias 不為 0 但卡名與主卡不同的例外條目不合併,記入建置報告供人工檢視。
- **輸出格式**:單一 `cards.json`,UTF-8,一卡一物件,以卡片密碼為主鍵、依密碼排序,鍵順序固定。欄位:`id`(主卡密碼)、`alt_ids`(異圖密碼陣列,無則空)、`name_zh`、`name_ja`、`name_en`(缺漏為空字串)、`desc`(繁中卡文原文)、`type`、`atk`、`def`、`level`、`race`、`attribute`、`scale`、`link_marker`、`setcode`、`ot`、`md_rarity`(N/R/SR/UR,未實裝 MD 為空字串)、`genesys_points`(整數,未列點為 0)。數值欄位保留 cdb 原始位元值(bitfield 不展開,解讀留給消費端;等級/刻度/Link 從 cdb 的複合 level 欄位拆出)。
- **差值更新**:以卡片密碼為 key 比對既有總表與新來源;新增卡直接併入,既有卡欄位有變動則覆蓋並記錄。輸出變動報告(新增清單、變動清單與變動欄位)。不處理刪除(官方卡不會消失)。
- **產出位置**:`cards.json` 置於 repo 內版本控管;來源 cdb 下載到不入版控的暫存目錄。
- **建置報告**:每次執行輸出統計——收錄數、排除數(含排除原因分類)、日/英卡名覆蓋率。

## Testing Decisions

- 只測外部行為:給定來源 cdb(用 `sqlite3` 程式化建立的迷你 fixture,數張代表性卡片),斷言輸出總表的內容;不測內部函式細節。
- 測試涵蓋的行為:
  - 正常整合:繁中+日英卡名正確對齊合併
  - 收錄規則:9 位數暫時編號的卡、Token/衍生物(`0x4000`)被排除
  - 異圖合併:同名 alias 條目合併進主卡且 `alt_ids` 正確;alias 指向不同卡名的例外不合併並出現在報告
  - 缺漏容忍:日英來源缺卡時欄位留空
  - 差值更新:新增卡併入、變動卡覆蓋且報告正確、無變動時輸出穩定(冪等)
  - 輸出穩定性:同輸入兩次執行產出逐位元組相同的 JSON
- 測試不碰網路、不依賴真實下載的完整資料庫。
- 本 repo 尚無既有測試可作 prior art;採 Python 標準庫 `unittest`,fixture 於測試內程式化建立。

## Out of Scope

- 效果 Tag 管線(拆效果句、embedding 分群、LLM 命名與貼標)——下一階段
- 查卡網站前端(進階查詢器、分頁展示)——下一階段
- 先行卡(`pre-release.cdb`)的收錄
- 韓文等其他語言卡名
- 卡圖下載與管理
- 禁限卡表、卡片價格等附加資料
- 自動排程更新(僅手動觸發)

## Further Notes

- salix5 網站的多語卡名是站長自爬 KONAMI 官方 DB 維護的(cid 對齊);本專案改用現成社群資料庫以避免維護爬蟲。
- `pre-release.cdb` 中先行卡使用 9 位數暫時編號(卡包代號+流水號),正式發售後會取得 8 位數密碼並移入 `cards.cdb`——這是收錄規則以 id 位數過濾即可的依據。
- 領域詞彙(卡片密碼、卡片總表、差值更新等)定義見repo 根目錄 `CONTEXT.md`。
