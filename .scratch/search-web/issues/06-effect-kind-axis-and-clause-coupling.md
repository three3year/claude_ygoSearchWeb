# 06 — 效果類型與必發選發軸

**What to build:** 「找出所有有誘發即時效果的卡」這個一般查卡站答不出來的問題,在這裡變成
兩次點擊。[[效果標記表]]花了 20 多張判定票判出來的 32,637 個[[效果句]]的[[效果類型]],
到這一票才真正有使用者。

本票同時把**句層耦合**做起來——這是整個站語意上最關鍵的一條:效果文關鍵字與[[效果類型]]
並用時,**必須命中同一個效果句**。一張卡的 ① 是誘發即時但不含關鍵字、② 含關鍵字但是啟動
效果,**不算命中**。使用者真正想問的是「一個會做某件事的誘發即時效果」,而不是「這張卡
某處有這四個字、另一處有個誘發即時」。

**Blocked by:** 04 — 效果文關鍵字與句層命中標亮

**Status:** resolved

- [x] [[效果類型]]十六值可篩選,分**怪獸側六類**與**[[魔陷卡效果]]十類**兩組呈現
- [x] [[必發/選發]]可篩選,且**只在已選的[[效果類型]]承載該屬性時才出現**
      (不會設出「永續效果是必發」這種永遠零結果的條件)
- [x] **句層耦合**:效果文關鍵字與[[效果類型]]/[[必發/選發]]取[[效果句]]層級的交集,
      一張卡只要存在一個效果句同時滿足全部句層條件即命中
- [x] 命中的那一個效果句進命中集合、被標亮,並掛上標示[[效果類型]]的 badge
- [x] 多條件並用時 badge 分得出這一行是因為哪個條件被選中
- [x] 接縫 3 測試(這是本票的核心,不是附帶):
      一張卡 ① 是誘發即時但不含關鍵字、② 含關鍵字但是啟動效果 → **不命中**;
      同一句同時滿足 → 命中,且命中效果句索引指向那一句
- [x] 接縫 3 測試:[[必發/選發]]只在承載的[[效果類型]]上生效

## Comments

2026-08-14 實作完成。改動橫跨三層:[[值域正典]](承載關係)、建置管線(`o` 欄位與一道新
檢查)、前端(引擎的句層條件、側欄兩個新軸、命中 badge)。接縫 1/2 測試多 7 條、接縫 3
多 8 條;`web/data.js` 重生(7.15 → 7.26 MiB,gzip 1.736 → 1.754 MiB)。

**[[必發/選發]]根本還沒進索引。** spec 的欄位表寫著 `o`,但票01 的最小索引只做到 `k`,
票02/04/05 都沒有用到它——這一票是第一個使用者,所以先補建置那一側:`o` 逐句進索引、
不承載的句子留**空字串佔位**(與 `ro` 同一個做法),整批都空時整個欄位省略。佔位而不是
壓縮成「只記承載的那幾句」:`tx` / `k` / `o` / `ro` 是同索引的四個陣列,壓縮之後第 2 個
`o` 對到第幾句就得再記一份對照表。

**「哪些效果類型承載必發/選發」住在值域正典,不是前端手抄的一張表。** 十二值(誘發即時
2速、誘發 1速、[[魔陷卡效果]]十值)寫在 `vocab.py` 的 `_OPTIONAL`,隨 `window.VOCAB`
出去。抄一份在 `query.js` 的話,某天多一個承載型的效果類型時那一組條件會安靜地不出現
——與 ADR-0008 要擋的「漏一個碼、某批卡從搜尋結果消失」是同一個失效模式,只是換了個
地方發生。正典自檢因此多一條:承載者對不到[[效果類型]]的成員即正典不合法。

**承載關係兩個方向都有人用,所以建置期多一道檢查。** 前端照它決定條件出不出得來;建置期
照它擋下「不承載的效果類型卻帶著必發/選發」——那是一個永遠零結果的條件在等著使用者設
出來。實測全表 0 筆(9,695 個帶值的效果句全部落在那十二值上),但這道檢查守的是標記表
日後的漂移,不是現在。

**句層條件的三態排除是「這一句不是那個類型」,不是「這張卡沒有那種句子」。** 同一顆鈕在
同一個軸上不能有兩種語意,而句層的單位是句:搜「效果文=特殊召喚 + 排除啟動效果」要的是
「一個不是啟動效果的特招效果」,不是「一張完全沒有啟動效果的卡」。副作用是排除型條件單獨
使用時會把幾乎每一行都標亮(每一行都滿足「不是啟動效果」),那是排除型條件的本性,不是
標亮壞了。

**句層耦合的數字**:效果文搜「特殊召喚」得 6,973 張;加上效果類型=誘發即時(2速)後,
**同句**是 423 張,而「卡裡某處有這四個字、某處有個誘發即時」是 875 張。一般查卡站給的是
後者——多出來的 452 張是兩件無關的事湊在同一張卡上。這個差額就是這一票的全部意義。

**必發/選發那一組條件,一顆效果類型都沒選時仍然顯示。** Story 25 的字面是「只在我選了承載
它的效果類型時才出現」,但它寫的理由是「不會設出永續效果是必發這種永遠零結果的條件」。
一顆都沒選時「必發」自己是有結果的條件(1,830 張卡),照字面收起來的話,Story 24 的
「找必須發動的效果」得先點滿承載的十二顆鈕才問得出來——同一個結果、十二次點擊。因此規則
是:**已選(包含)的效果類型全都不承載時才收起來**。排除不算已選(排除永續效果之後,命中的
句子仍然可能是承載型的)。spec 的「搜尋語意」已同步改寫。

**命中 badge 寫的是「這一行自己的值」,不是條件的名字。** 效果文那一種寫死是「效果文」
(關鍵字對每一行都一樣),效果類型與必發/選發則從該行的 `k` / `o` 讀——效果類型選了誘發
即時+誘發兩顆時,命中的兩行本來就不是同一個詞,badge 寫「誘發即時效果(2速)」才答得出
「這一行為什麼被選中」。多條件並用時是「效果文・誘發即時效果(2速)・必發」。這不違反票04
的「呈現層不自己判命中」:判命中的仍然只有引擎,呈現層只是把那一行的值寫出來。

**效果類型條件掃得到素材指定行,效果文關鍵字仍然不掃。** 不掃素材行是**關鍵字**的規則
(574 張融合怪獸的素材寫法會淹掉答案),不是「素材行在句層不存在」——選效果類型=效果外
文本的人要看得到那 2,358 行。兩者並用時素材行自然不會命中,因為關鍵字那一關就過不去。

**側欄的排列改成句層條件在前。** 效果類型與必發/選發排在 `#critParams` 的最前面,緊接著
上面的效果文框,大類與卡片參數往下移。引擎的分界是卡層/句層,而這三個是全部的句層條件
——它們並用時取的是同一個效果句,排在一起才看得出那是**一組**問題,而不是三個獨立的篩子。

**沒有加 DOM 測試**(spec 的 Testing Decisions:DOM 渲染走人工驗收)。可測的形狀是純的
兩塊:`Query.optionalAvailable(效果類型選擇)`(那一組條件出不出得來的規則,與票05 的
`Query.axes()` 同一個理由——沙箱沒有真的 DOM,DOM 那一層只是照答案收合)與引擎本身。
呈現層的 badge 另以帶快取的 DOM stub + 真實 `data.js` 冒煙對過:單條件、三條件並用
(`效果文・誘發即時效果(2速)・必發`)、排除型條件命中不承載的句子(badge 只剩效果類型)
三種形狀,關鍵字上色與標亮都落在同一行。
